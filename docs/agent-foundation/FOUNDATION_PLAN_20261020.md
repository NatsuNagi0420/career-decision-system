# TypeScript 自研 Agent 底座路线

## 0. 状态和适用范围

> **2026-10-21 实施更新：** 原路线已进入落地阶段。默认入口已切换为自研 TypeScript 本机服务，旧 Python 业务单独保留。本文下方描述 2026-10-20 制定路线时的起点，不应再把“未实施”视为最新状态。已实现内容、实测结果及未验证边界见 IMPLEMENTATION_20261021.md 和 agent/README.md。

日期：2026-10-20。依据用户最新意图：借鉴开源思想，用 TypeScript 编写自有 Agent 底座，优先在沙箱中执行，验证通用任务后加入职业规划能力。此文是新增路线和验收方案，不是已完成的架构说明。

当前可运行系统仍是 React / TypeScript 前端 + Python / FastAPI / LangGraph + MySQL / SQLite。旧代码、账号、数据库、穗奈素材和现有接口均保留，本轮没有迁移。docs/v2/PROJECT_GOAL.md 中“一个 Python 服务”“不做万能 Agent”是 v2 已有阶段的范围；本路线改变的是后续执行层目标，不能据此宣称 v2 基线已经替换。

前一份选型报告推荐先验证 LangGraph TypeScript；用户现在更明确地选择“自己写底座”。因此新的优先方案是自有 TypeScript 执行核心，而不是默认迁入一个完整框架。模型 SDK 和现成沙箱仍可以复用，不把“自研”误解为重写模型协议、容器系统、数据库或文档格式。

## 1. 产品边界

### 目标：通用执行内核，不是先做一个无限范围的通用助手产品

- 通用内核：对话和任务状态、模型决策、工具执行、事件、审批、预算、中断、成果版本。
- 求职产品：画像、岗位证据、学习路线、题目练习、简历事实与编辑规则、导出模板和穗奈交互。
- 内核不得硬编码“只有职业规划”；但第一阶段仍必须用一条脱敏求职材料任务做回归样例，防止抽象底座与产品需求脱节。
- 是否是可工作的 Agent，以真实工具记录和可检查成果为依据，不以自称完成、框架名字或多 Agent 数量为依据。

“先通用、后特化”是实现顺序，不意味着先对外发布一个通用助手、再重新寻找求职产品方向。

## 2. 目标结构

~~~text
现有 React + TypeScript / 穗奈界面（保留）
                   │ HTTP + SSE，经接口兼容层接入
TypeScript 本机控制服务（可信控制层）
  ├─ 会话、任务、预算、状态和事件
  ├─ 模型适配：云端模型调用；凭据不交给生成代码
  ├─ 自有执行循环：决定 → 校验 → 执行 → 观察 → 继续/追问/结束
  ├─ 策略和审批：由程序执行，不由模型自行授权
  ├─ 成果与版本：真实文件、来源、状态和导出记录
  ├─ 沙箱适配器 ──→ 隔离执行区（受限、不可信）
  │                  ├─ 输入资料的任务副本
  │                  ├─ 文件与脚本操作
  │                  └─ 输出、退出码、执行日志
  └─ 授权本机桥接：选择输入 → 导入副本；确认成果 → 导出
                   │
职业能力层：画像 / 岗位分析 / 学习与练习 / 简历编辑与导出
~~~

初期在一个独立 agent/ 目录中实现一套 TypeScript 服务，内部按职责分模块；不为每个模块创建微服务或另一套前端。独立沙箱运行时属于基础设施，不属于另一套业务后端。

现有 web/src/api/client.ts、web/src/state/frames.ts 与 web/vite.config.ts 为接入边界。兼容范围包括鉴权、错误、seq、帧含义、审批和成果状态；连续会话和文档版本仍可能带来局部接口或 UI 变化，不能保证前端完全零改动。

## 3. 自己写什么，借鉴什么

| 部分 | 自有实现职责 | 参考与限制 |
| --- | --- | --- |
| 执行核心 | 循环、状态机、预算、工具调度和事件 | 参考 Pi 的小内核与分层思想；不照搬其默认进程权限 |
| 模型适配 | ModelAdapter、调用计量、工具结果返回 | 可选择一套成熟模型 SDK，不与多套 Agent 框架叠加；先测当前模型网关 |
| 工具契约 | 输入和输出运行时校验、权限声明、错误和成果 | TypeScript 类型不能代替对模型参数的运行时校验 |
| 长任务工作空间 | 同一任务的输入、进度、文件与成果 | 参考 DeerFlow 的任务组织，不整体移入其服务体系 |
| 沙箱适配 | 创建、执行、取消、导入、导出、清理和健康检查 | 初期评估本机 Linux 容器；借鉴 OpenSandbox 生命周期和执行接口，不自制“虚拟机” |
| 求职能力 | 结构化资料、规则、验证器和专用工具 | 后续接入同一底座；不是仅换一句系统提示词 |

Pi 当前官方仓库说明其默认没有文件、进程、网络或凭据权限限制。它适合参考小内核，不适合被当成现成安全边界。OpenSandbox 官方资料说明其运行时支持 Docker 和 Kubernetes 等后端；本轮只读资料，没有安装和运行这些项目。

如未来复用具体源码，需要固定版本、核对许可证并保留要求的声明。本轮没有复制第三方源代码，也没有根据语言不同声称原创或赛题合规。

## 4. 第一版内核的有限能力

### 第一批必须有

1. 同一 conversationId 下可有多次 run，反馈对应同一任务与最新成果；不得每句话都无条件开启失忆任务。
2. 工具：列文件、读文本、搜索、在任务工作区写文件、沙箱命令执行、向用户追问。
3. 控制：步骤/时间/模型预算、取消、工具超时、循环终止和明确的失败状态。
4. 事件：记录真实工具名、参数摘要、执行结果、退出码、成果引用和 seq；不把模型私有推理当执行日志。
5. 成果：从真实存在的文件登记，记录版本、文件大小或摘要、任务来源；不能仅因模型说“已导出”就展示下载成功。
6. 持久化：保存会话、run、工具调用与审批；先定义存储契约，再验证本地存储实现，不触碰现有业务库。
7. 副作用：为审批和有副作用工具设置明确标识及重试规则；执行状态不确定时先核对，不能重放一次就重复写入。

### 后续接入，但现在不抢先承诺

- 受控联网和沙箱独立浏览器：检索、阅读、来源记录；不直接复用用户日常浏览器登录态。
- 复杂 PDF、Word 等文档解析与导出：需实际检查中文字体、布局和文件可编辑性。
- 原生桌面点击、个人浏览器自动化、自动安装宿主程序、跨应用操作。
- 多 Agent、插件市场、持续后台自治、自动投递简历或自动发送消息。

已有普通本机服务并不等于已经具备这些权限或工具。

## 4A. 模型接入与最小 Agent 补充

依据用户最新补充：支持官方预置服务，也支持用户自行提供第三方 OpenAI 兼容接口，包括 New API 网关；第一阶段先保证对话、规划、真实工具执行和结果交付。本节为确定的需求与拟实施接口，尚未创建 TypeScript 运行时、模型设置页面、凭据存储或官方中转服务。

### 两种明确的使用模式

| 模式 | 用户看到什么 | 连接和凭据的归属 |
| --- | --- | --- |
| 官方服务 | 选择官方预置模型，不填写上游 Key | 本机 Agent 通过本产品的用户认证访问官方中转；上游地址、模型和 API Key 仅配置在我们控制的远端服务 |
| 自定义服务（BYOK） | API 地址、API Key、模型名称，另有高级协议设置 | 本机 Agent 直接访问用户明确选择的接口；用户 Key 不经官方中转，存储与使用均限制在授权范围内 |

“官方内置”指预置调用入口，不是把官方上游密钥装进前端、本地 .env 或安装包。用户控制自己的电脑，本地打包或混淆不能使我们的共享上游 Key 对用户保密。开发者自用的私有配置与分发给用户的官方服务是不同情形。

官方中转是普通受保护的模型 API 服务，不运行用户的桌面或任务沙箱；它需要鉴权、额度、限流、计量和固定上游策略，不是开放代理。其基础设施与运营成本不能因为“任务在本机”就忽略。

现有版本的统一开发配置入口是 server/.env，字段见 server/.env.example：LLM_PROVIDER、LLM_BASE_URL、LLM_API_KEY、LLM_MODEL。它是当前 Python 服务的统一配置，不是已实现的每用户 BYOK，也不是已建成的官方中转。新服务完成后另提供确切部署配置路径，本轮不读取或修改实际 .env，不要求用户现在提交密钥。

### OpenAI 兼容的范围

- 第一优先适配 Chat Completions 的消息、tools、工具结果及流式/非流式响应；设置中明确 apiKind，给 Responses 适配保留独立入口，不靠 URL 自动猜测协议。
- New API 官方文档给出通常以 /v1 结尾的 Base URL、Bearer API Key、model 与 /chat/completions 调用。地址规范化避免重复 /v1，也不将完整完成请求地址当作 Base URL。
- 模型名可以手工输入；模型列表获取失败不等于聊天一定不可用。网关模型别名以该用户被授权的列表为准，不硬编码某一家模型。
- “OpenAI 兼容”不能当作“任何模型的全部能力都兼容”。模型、网关版本、渠道与 API 形态可能限制工具、流式和结构化输出；目前 OpenAI 官方也明确存在要求 Responses 才可调用工具的模型。
- 连接测试分清认证/文本、流式、工具调用与工具结果续答。不仅测试一句问候就显示“Agent 可用”。测试工具不产生文件或外部副作用，测试调用可能产生供应商费用。
- 不支持工具的配置可以明确标为“仅聊天”；不得谎称正在执行任务。流式不可用但非流式工具验证通过时，可以使用明确的非流式路径。
- 不自动把同一个 Key 发往另一域名，不因第三方失败就偷偷切到收费的官方服务；配置变化后重新验证相应能力。

### 密钥与数据边界

- 浏览器设置提交后不回显完整 Key，不把 Key 持久保存在 localStorage、任务正文或普通日志；本机服务负责调用。
- 初版至少支持仅本次会话保存；长期保存须接入受评估的系统凭据存储，不以可逆字符串编码冒充安全加密。
- 模型 Key 不进入 system prompt、生成脚本、沙箱环境变量或工具执行日志；工具执行能力来自我们实现的工具，不来自 API Key。
- 自定义服务允许用户明确授权的本机/私有网关；外部连接默认 HTTPS，不关闭证书校验。服务端固定目标、重定向和私网访问策略需按本机与远端部署分别设计，防止把官方中转变成访问内网的代理。
- 选用外部模型或网关时，所发送的对话与选取资料会交给该服务处理；本机运行不等于资料不外发。界面应显示当前服务和模型，不对第三方可信程度作无依据保证。

### 对小白可说明的最小 Agent

用户侧只需理解：会聊天 → 复杂任务先说明简短步骤 → 真正调用工具 → 看工具结果再决定下一步 → 交付回答或文件。简单问候和知识问答不必强制制定计划或调用工具。

第一版必须额外守住四件事：记住同一任务与最新成果；不会把“打算做”说成“已完成”；失败、缺资料和取消时如实处理；限定权限和预算，避免一直执行或无限调用模型。规划是可以随结果调整的短计划，不要求单独规划模型、多 Agent 或展示私有思维链。

具体回归样例：“读取导入的几份文本，生成总结文件” → “再短一点” → “只改第二段” → “导出”。检查真实读写、同一成果版本、预览/导出，以及错误和拒绝后的状态。这是初版验收范围，不代表当前已实现。

后续职业能力使用同一底座，但增加资料结构、岗位证据、学习节点、练习记录、简历事实约束和模板；不是重新做一个 Agent，也不是只换一段提示词。

本节资料核对：New API 使用 API 与游乐场；OpenAI API Overview 的 Authentication；OpenAI Function calling 的工具执行循环及 API 形态限制。均为官方资料，本轮没有发送模型请求或真实密钥。

## 5. 沙箱优先是强约束

### 信任边界

- 可信控制层在模型调用与沙箱之外校验权限。模型生成的脚本、外部网页、文档和技能内容均不具有提权资格。
- 沙箱只得到已选择输入的任务副本，不直接挂载整个 D:、用户目录、项目仓库、数据库或 .env。
- 不把模型 API key、数据库凭据、宿主 Docker socket 或管理员权限交给执行区。
- 沙箱命令工具不提供“执行失败就改成本机 PowerShell”的降级路径；沙箱不可用即明确阻止该工具。
- 模型可以建议工具参数，但不能选择任意宿主挂载路径、特权容器参数、镜像或网络模式。基础设施配置由可信代码固定和校验。

### 初期隔离配置的验收要求

- 固定受信镜像或摘要；非 root；去除非必要 capabilities；禁止 privileged 和 host PID/network；保留内核安全配置。
- 默认禁网，按任务显式放开受控联网。云端模型调用由控制层承担，不因此给任意生成脚本放开外网。
- 内存、CPU、进程数、时长和输出大小有限额。磁盘增长需验证具体存储后端的可执行限制，不把普通 CPU/内存参数说成硬磁盘配额。
- 只允许工作目录和必要临时目录可写；导入、导出检查路径规范化、软链接/重解析点、目录逃逸与文件大小。
- 本机服务只绑定回环地址，仍验证会话与请求来源。模型密钥只在服务端配置，不进前端代码或普通日志。
- 审批绑定具体动作、目标路径及当前成果版本。用户允许一次导出，不代表模型可以任意写本机文件。

Docker 提供命名空间和资源限制，但其安全性依赖配置、挂载、daemon 访问和内核。这里的容器是降低风险的隔离方案，不保证对任意恶意代码绝对安全。正式面向不可信多用户时，应再评估更强的运行时或虚拟机隔离。

工作目录限制、Node.js vm、一个普通子进程或 WSL 发行版本身，都不等于此处定义的安全沙箱。Node.js 官方明确 vm 不是用于运行不可信代码的安全机制。

## 6. “能工作”的验收任务

以下均为计划案例，不是本轮已通过测试：

| 场景 | 应当观察到的真实结果 |
| --- | --- |
| 文件整理 | 读取提供的几份文本并产生可打开的总结文件，保留来源 |
| 数据与代码 | 在沙箱执行统计脚本，退出码正常，输出与固定样例的预期一致 |
| 连续修改 | 用户要求“改短一点”“只改第二段”时，新版本建立在同一任务的最新文件上 |
| 工具失败 | 命令或解析失败时显示具体阶段，不伪造成功成果 |
| 缺资料 | 主动追问，而不是编造缺失内容 |
| 隔离拒绝 | 试图访问未导入资料、宿主凭据、网络或任意本机目录时被阻止 |
| 审批拒绝 | 用户拒绝导出或覆盖后，本机目标未被写入 |
| 取消与恢复 | 取消会停止执行；重连不会重复展示，恢复不会盲目重做不确定副作用 |
| 求职回归样例 | 读取脱敏简历文本和 JD，追问、改写指定段落并生成文本成果；领域质量另行评估 |

单元测试使用可脚本化模型和假沙箱，仅证明控制逻辑；还必须跑真实容器与真实模型样例。三者结果分开记录，不能把 mock 测试通过当作沙箱或模型能力验收。

## 7. 实施顺序

1. 明确协议与只读环境预检；新增独立目录，不改旧系统默认入口。
2. 编写自有 TypeScript 小内核与受测工具协议，先用假适配器测取消、失败、预算与审批。
3. 准备可用沙箱运行时，验证真正的隔离、限额和禁网；再接真实模型与工具。第二步不必等待沙箱安装完成，但不能伪称已完成第三步。
4. 跑上表中的有限任务，接入现有前端的执行过程和成果展示。
5. 加入受控检索与领域能力：画像、岗位证据、学习路线、练习与简历。领域规则进入工具、数据与验证器，而不只是提示词。
6. 确认功能与数据兼容之后，再决定旧 Python 服务如何退场；活动任务与 Python checkpoint 不假定能直接迁移。

当前不安排全量重写界面、清库、强制安装系统组件或迁移全部账号。沙箱的安装与 Windows 组件配置作为下一项明确实施工作处理，可能涉及管理员权限和重启，不能称为“已自动准备好”。
