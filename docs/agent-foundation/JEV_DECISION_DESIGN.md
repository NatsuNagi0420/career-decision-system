# Jev 职业判断方案

日期：2026-10-28。状态：第一版业务闭环已接入，本机完成真实画像线索与确认更新验收；准确率、长尾案例和批量延迟仍需样本评估。

## 1. 产品结论

Jev 适合成为穗奈的结构化判断层。它接收共同材料 `state` 和一组独立的 `questions`，返回概率、分类和评分；主模型继续负责自然对话、材料抽取、解释和文字生成，程序负责约束、组合评分、授权和持久化。

用户能体验到的特色应是：依据可查看、未知项可补充、结论会随实践反馈更新。Jev 的名字和模型速度本身不足以构成产品差异化。Jev 判断的是材料对结论的支持程度，不能验证用户经历真的发生，也不能测出一个人的真实能力或录用概率。

第一版目标闭环：

```text
用户谈到经历
  → 主模型抽取带原话出处的候选事实
  → 程序验证出处与引文
  → Jev 批量判断：经历 / 计划 / 偏好 / 不足 / 冲突
  → 保存有状态的画像候选，保留已确认资料
  → 对已检索的岗位参考评估证据与缺口
  → 穗奈只追问一个最有价值的问题
  → 用户补充经历或完成练习
  → 受影响的判断重新计算
```

候选自动保存与已确认画像写入是不同动作。第一版延续当前确认边界，不把高概率判断直接写成已确认技能，也不要求用户逐条填写画像表单。自动确认哪些低风险字段，需要另行定义策略并经过样本评估。

## 2. 核实到的模型能力

| 能力 | 适合用法 | 使用限制 |
| --- | --- | --- |
| `noul` | 判断“当前引文是否支持已完成 React 项目” | 返回命题成立概率；不等于证据经过外部核实 |
| `choice` | 在已有标签中选择经历、计划、偏好、信息不足等类别 | 必须提供 unknown / insufficient 等退出选项，不能强迫选择职业方向 |
| `score` | 对证据完整度、岗位相关性等独立维度按档评分 | 档位要有明确行为标准；不能直接命名为人的能力分 |
| 共享 state、多 questions | 一次比较多个岗位维度或多条事实 | 同批问题独立，不可让后一个问题读取同批前一个问题的答案 |
| 概率与 confidence | 决定继续追问、展示暂定建议或进入人工核对 | 命题概率与判断置信度不同；阈值需要本产品样本校准 |

官方资料将 Jev 定位为结构化判断模型，不承担普通聊天和自由文本生成。当前项目的 `/v1/systemone` 适配接受文本及 JSON 材料，简历、图片与源码仍先由对应解析器或主模型处理，不能将附件直接塞入现有接口。

官方文档存在模型版本差异：截至本次查阅，模型页已列出 Jev 1.14；本项目 2026-10-28 连通性记录实际返回 `jev-1.13.0`。当前中转别名 `Typesafe-jev` 不足以保证底层版本不变。评估及缓存必须记录实际模型版本，不能未经验证就复用其他版本的阈值。

速度也需要分开看：官方资料宣传推理端的低延迟；本机已有一次“两问题”请求耗时 1499 ms，包含本地服务、网络和第三方中转。单次连通测试不代表岗位批量评估的延迟分布或准确率，不能宣传固定毫秒级响应。

还需要专门评估中文：官方模型页说明英语是主要训练语言，中文等语言支持但表现并不等同。我们的验收集必须包含真实中文求职表达、含糊肯定、否定、更正、技术中英混用及用户说的“我都可以”。可以比较中英文问题模板，但保留用户中文原话作为事实依据，翻译不能替代原始引文。

## 3. 优先落地的判断任务

### P0：候选事实与画像证据校准

输入只包含候选事实、相关用户原话、对应字段的已保存内容。每条事实带 `source_id`、消息或材料版本和逐字引文，不读取助手建议作为用户事实。

先由程序核验引用存在，再由 Jev 判断：

- 这是否为用户已经做过的事情，还是未来计划、兴趣或假设？
- 引文是否充分支持候选事实的强度？
- 是否与既有资料发生语义冲突？
- 信息是否不足，应先追问？

采用窄问题：对“做过项目”和“熟练掌握技术”分别判断，不能把两个命题混成一个概率。低置信度先留为待了解，不直接认定用户不具备能力。冲突同时保留双方来源，由用户更正或主模型进一步澄清。

这一层不做学历真实性鉴定、不猜测人格、不为聊天中的模糊表达打能力等级。

### P0：岗位证据对照与排序

候选岗位必须先从数据库或用户提供的真实 JD 获取。全文解析结果保留出处；岗位库现有日期、状态、城市及求职阶段过滤仍然有效，Jev 不得偷偷放宽条件。

对每个岗位分别判断：

1. 已有经历对核心要求的支持程度。
2. 项目经历与岗位职责的相关性。
3. 用户明确表达的偏好与岗位的符合程度。
4. 尚未了解的关键要求，以及适合验证的缺口。

确定性数值、日期、明确的城市和学历枚举比较由代码完成；歧义文本先结构化，无法确定时保留未知。硬性条件的明确不满足不能被其他维度的高分抵消。

第一版展示“支持较充分 / 部分支持 / 待了解 / 存在冲突”，不展示未经校准的匹配百分比。若内部需要排序，可用有版本的权重组合独立维度，连同信息覆盖率一起保存；缺失维度不能当作零能力。

每批例如 3 个岗位 × 4 个独立维度，共 12 个 questions。程序在返回后计算组合结果。不要为每个维度单独发请求，也不要把整个岗位库送入模型。

### P1：选择下一条追问与下一步验证

由主模型根据现有材料提出最多 3 个可问的问题或可执行的小行动，每个候选必须明确想减少哪项不确定性、用户成本以及实际可执行条件。

Jev 对候选的相关性、减少当前不确定性的预期价值、用户负担按独立标准评分；代码在允许的候选中选择，主模型用穗奈的语言问出来。这里是启发式的追问价值评估，不能宣传为已经计算出严格的信息增益或保证最优。

例：用户实际做过 Python 清洗数据，同时想学 React，但缺少前端项目。优先询问 Python 项目中独立完成了什么，或提供一个短的前端验证任务；不能将“想学 React”记成已经具备 React 项目经验，也不能据此断言不适合前端。

无新信息的闲聊和空闲提醒不触发这层。不要读取尚未发送的输入框草稿。

### P1：简历的事实与取舍检查

先完成画像、事实底库、JD 对齐，再让 Jev 判断：

- 经历与目标要求是否相关，应重点展示、压缩还是暂不使用。
- 改写后的每个主张是否被已确认事实支持。
- 是否把学习计划、团队成果、示例数字写成用户已完成的事实。

主模型负责 STAR 改写与解释，程序负责数字、日期、引用以及 JSON 结构校验。Jev 低置信度或服务不可用时不能将正文标记为“检查通过”；保留草稿，让用户核对，不默默确认或导出。

### P2：学习路线与实践反馈

Jev 判断岗位要求的优先级、已有证据和缺口类型。学习资源、先修关系、可用时间及完成状态来自资源库或代码；主模型写出教学说明。

用户提交作品、题目表现或行动结果后，重新评估对应技能的实践证据，再更新画像候选与岗位对照。单次做题、代码中存在某个库都不等于用户已经掌握该技能；需要区分代码内容与用户本人贡献。

## 4. 与本地 Agent、官方服务的分工

```text
5173 / 打包后的 WebUI
       ↓
8110 本地 Agent
  - 获取用户授权的材料片段
  - 抽取、验证引用、保存候选事实和实际用户确认
  - 管理版本、结果缓存和界面事件
       ↓ 官方模式
8120 官方服务
  - 持有上游密钥、模型路由和领域问题模板
  - 受限的职业判断请求 → Jev
  - 返回结构化结果，不连接用户电脑、不直接写本地业务库
       ↓
上游第三方中转 / Typesafe-jev
```

建议新增任务级接口，例如 `POST /v1/career/decisions`，客户端提交任务种类、事实及出处；服务端选择问题模板和真实模型。该接口已实现；通用 `/v1/systemone` 继续保留。不要依靠主模型自行决定是否拼 Jev 请求，也不要把问题模板散落在聊天 prompt、各个工具及前端。

实际统一入口为 `CareerDecisions`（`agent/src/domain/career/decisions.ts`）：任务模板、输入验证、Jev 调用、结果策略、审计均通过一个入口。8110 不接收主模型任意提供的 Jev URL、模型名称或后续写库指令。返回的动作建议仍需通过本地代码的权限与版本检查。

用户自配模型时默认只调用自己的服务，不静默发送材料至官方 8120。自配模式可继续使用主模型和确定性校验；界面需准确说明该次判断的实际提供方式。启用官方 Jev 增强需要已有授权覆盖该数据发送，或明确增加授权选项。

所有模型服务只能接触实际提供的片段。Jev 的使用同样涉及外发数据，不能声称本地运行时资料完全不出电脑。

## 5. 调用时机、延迟与成本

| 事件 | 处理 |
| --- | --- |
| 新增或更正了可引用的职业事实 | 批量判断本次候选，不重新处理全部历史 |
| 请求岗位推荐或选择了目标岗位 | 在确定性检索后评估少量候选 |
| 画像、JD、实际项目贡献或实践结果变化 | 只令依赖这些内容的旧判断过期 |
| 普通闲聊、眨眼动画、鼠标悬浮、空闲状态 | 不调用 Jev |
| 请求取消、编辑重发、授权撤回 | 取消未完成请求；旧分支结果不能写入当前状态 |

同一批问题共享必要材料，但问题之间必须独立。第二阶段需要第一阶段结果时，由代码发起下一批，不能依靠同一批问题互相读取结果。

缓存键至少包含账号、任务种类、材料内容指纹、问题模板版本、策略版本和模型版本。中转别名可能漂移，缓存要能主动失效；不跨用户复用私人判断。已确认资料的变更不得继续命中旧判断。

8120 已为职业判断配置独立并发通道，聊天与 Jev 仍共享每日总预算；职业判断按实际问题数量预留有界预算，并在中断或失败时释放占用。主回复结束后再整理画像，减少对聊天等待时间的影响。

需要记录实际输入输出用量和中转计费，不能用 TypeSafe 官网价格代替用户当前第三方中转价格。前端发送完已生成的文字后可后台处理低风险候选；画像与岗位展示应区分“正在校准”和“已更新”，不阻塞全部聊天。

超时、服务不可用、返回非法类型、缺失问题答案均为未完成判断，不能默认通过。聊天可以继续；依赖该判断的候选保持未检查或等待处理。允许有界重试，写入保持幂等，不能让一次 Jev 故障拖垮主对话。

## 6. 结果、阈值与安全边界

每份判断至少保存：

```text
id / user_id / conversation_id / run_id
任务种类 / 模板版本 / 策略版本 / 实际模型版本
材料版本与指纹 / source_id / 原始引文
questions / answers / 命题概率 / confidence（若接口返回）
使用的阈值 / 程序最终动作 / 耗时 / 用量 / 完成或失败状态
```

画像或岗位依据变化、消息编辑重发时，旧判断只能作为历史，不可继续冒充当前结果。删除会话时按既有生命周期清理该会话的决策日志；独立保存的用户档案按其规则保留，不能无期限保留已删除会话的完整正文副本。

`noul=0.9` 表示模型在给定材料和定义下对命题的概率估计；不等于该用户真实具备技能的概率，也不等于九成准确率。`choice` 的选项概率与 `confidence` 也不是同一指标。无需依赖可选 confidence 才能决定“信息不足”；模板必须允许选择未知。

不设一个覆盖所有业务的万能 0.8 阈值。候选展示、已确认技能、简历正文和代表用户行动有不同影响。第一版高概率也只能通过证据校验并形成候选，不能越过现有用户确认和权限边界。阈值、权重及误判代价需要人工标注的求职样本评估。

原文、JD、网页和项目代码都是待判断数据。Jev 已公开的 1.13 局限包括 prompt injection、算术、日期比较和复杂间接推理。因此它不能替代引用校验、工具授权、目录隔离和确定性硬规则。避免把“来源中要求模型给高分”变成有效指令；既有结构化输出也不能防止语义被诱导。

## 7. 前端表现

继续围绕穗奈主对话，不新增常驻的大型评分工作台。

- 画像：已有字段旁按需查看“原话 / 已确认 / 待了解 / 有冲突”，保持来源可追溯。
- 岗位卡片：突出下一步；展开后列出支持证据、待补项和判断时间，沿用收藏与岗位详情。
- 穗奈气泡：根据当前最有价值的问题提出建议；不自动发送用户消息、不擅自切换任务模式。
- 简历预览：在可疑改写处提示“这句话还缺依据”，允许补充事实或降低表述强度。
- 执行面板：显示“正在对照岗位要求”“已完成 12 项判断”等真实事件；详细问题与结果默认折叠，不假装展示模型私有推理过程。

仅在用户需要理解时解释状态，不额外堆叠多个模型名、标签、副标题或技术说明。

已经存在：

- `agent/src/systemone.ts`：结构化请求与结果校验，保留概率零值和分数小数。
- `agent/src/relay-app.ts`：8120 的 `POST /v1/systemone`，沿用官方鉴权、并发限制和每日预算。
- `agent/test/systemone.test.ts`：接口契约、鉴权和错误回归。
- `logs/official-text-model-test-20261028-151200/results.json`：本次日期已有 Jev HTTP 200 及 1499 ms 单次测试记录。
- 职业档案与待确认提议、离线岗位库、简历事实引用及工具边界。

本次已接入：

- 共享任务契约、问题模板、严格结果校验及 `POST /v1/career/decisions`。
- `CareerDecisions` 领域服务，持久保存带原话的候选、判断记录、活动状态和简历检查。
- 官方回复后的后台整理：经历、计划、偏好与现实条件分开；主模型的单条非法候选不会使其他有效候选丢失。
- 主对话“刚聊到”支持原话展开、记下、忽略与更正；右侧展示成长档案及待核对数量。
- 追问及整理进度按当前会话显示；新发言后旧追问失效，点击追问进入用户回答草稿。
- 岗位参考批量对照与下一问；材料变化标记过期，后续对话或“重新对照”使用最新材料重评。
- 简历全文及局部改写核对，区分部分检查、需核对、未完成和结果过期。
- 用户自配模型不发送到官方 Jev；用户确认前不改正式画像；失败时保留原对话和未核对状态。
- 主模型输出的 plan / learning_plan 字段仅规范为目标字段；Jev 任务入口仍严格校验。

真实验收使用独立账号与合成职业材料：形成 4 条候选，学习计划没有进入已掌握技能；点击一条经历后成长档案更新、候选剩 3 条。验收日志位于 `logs/jev-career-integration-20261028-1818/`。

仍需继续评估：真实中文求职样本的误判率、不同问题模板的稳定性、批量岗位对照的 p50 / p95 延迟及实际费用。一次连通验收不能证明业务准确率。

本次实现对应的三段体验：

1. **画像证据校准**：明确真实经历与计划的区别，已有对话原话可以形成带出处的画像候选；更正后重新判断，已确认资料不被覆盖。
2. **岗位对照 + 下一问**：三份岗位共享材料批量判断；卡片展示依据和缺口；穗奈围绕最影响判断的未知项继续对话，补充后重评。
3. **简历检查 + 实践反馈**：取舍和改写接受事实支持检查；用户提交实际行动结果后复用同一判断服务。

不需要为每个动作建立一个新 Agent。先复用当前职业领域适配层，让同一份事实底库、岗位原文和决策记录贯穿三次交付。

验收关注两类结果：程序测试覆盖引用、跨账号、非法响应、取消、过期结果、幂等及失败不自动通过；人工样本关注计划误判为能力、相关证据遗漏、对未知的保留率、下一问是否有帮助、p50/p95 延迟和单次任务成本。假响应测试通过不能证明 Jev 业务准确率。
