# 测试账号与云端资料清理

## 当前事实

当前服务器同时维护两类数据，但不是让用户注册两套账号：

- 官方账号与用量：/var/lib/qingsuiji/relay/relay.sqlite。保存账号、令牌摘要、用量和计费记录。
- 云端工作区：/var/lib/qingsuiji/agent/agent.sqlite。保存官方账号映射、设备、同步会话、云任务、画像、简历、文件与记忆。
- PC 还有自己的工作区数据库和用户原始项目。删云端同步副本不会自动抹掉 PC 原始资料。

目前没有完整的“清空整个账号”产品入口。已有的对话永久删除不会同时抹掉独立画像、简历、全部记忆、设备和账单，因此不能把它称为账号清空。

## 测试结束后推荐选择

| 目的 | 做法 | 保留 |
| --- | --- | --- |
| 保留测试账号，从空白工作区再测 | 清空指定账号的工作区数据，并撤销原设备连接 | 官方账号与必要用量账目、公共岗位库 |
| 淘汰一个临时测试账号 | 先停用官方账号并撤销其全部令牌，再清理关联工作区 | 必要审计账目，是否匿名化另行决定 |
| 正式用户要求注销 | 单独制定数据保留、备份到期和计费审计规则 | 不能把测试清理当成正式注销 |

不要直接删除 agent.sqlite、relay.sqlite、整个 /var/lib/qingsuiji 目录，也不要按用户名模糊匹配批量删除；会影响其他账号、岗位库或计费。备份也仍含历史资料，清理后需要按约定保留期到期移除。

## 先盘点，不删除

工具 scripts/ops/audit-test-accounts.mjs 是只读的，只输出账号名称、标识、表记录数量，不输出聊天、记忆正文、密码或令牌。

在现有 Ubuntu SQLite 部署中，以有权只读数据库的管理员执行：

~~~bash
sudo /usr/local/bin/node /opt/qingsuiji/ops/audit-test-accounts.mjs \
  --relay-db /var/lib/qingsuiji/relay/relay.sqlite \
  --hub-db /var/lib/qingsuiji/agent/agent.sqlite \
  --username 需要盘点的精确账号名
~~~

可重复指定 --username；不指定时枚举官方账号。工具不提供 --apply 或删除功能，不会误触清空。未来迁移 PostgreSQL 后需更换盘点适配器。

## 真正执行清理前的顺序

1. 明确指定账号与目标：只清工作区，还是停用账号；列出要保留的账号。
2. 暂停相关账号的同步、撤销旧设备绑定并停止任务，避免离线 PC 把旧资料再次上传。若要跨端清空，还须单独清理各 PC 的该账号副本；不能动绑定的原始项目目录。
3. 同时对官方账号库和工作区库做 SQLite 一致性备份，备份留在服务器受限目录。现有 qingsuiji-hub-backup 与 qingsuiji-relay-backup 服务可做快照，但两库不是分布式事务，维护窗口中应停止写入。
4. 按精确官方账号 ID → account_identities 的 issuer/subject → 工作区 user_id 建立范围；用事务清理该范围的会话子表、任务、文件内容、画像、简历及历史、记忆和同步状态。FTS、来源、关系、队列、设备和无外键的 remote_* 表也必须涵盖；未知 schema 时停止，不猜测。
5. 只删除已核对归属、且位于服务数据目录下的生成文件。跨端副本由用户单独确认；原始项目不删除。保留 catalogue_*、其他账号、官方模型配置与必要计费记录。
6. 检查外键与数据库完整性；重新启动服务，确认目标账号空白、其他账号数量未变、公共岗位库仍在。需要彻底淘汰的测试账号保持 suspended。

本次改版只添加只读盘点与此操作说明，未清空任何账号。后续应在明确账号范围后实现并验收带预演、备份和二次确认的实际清理命令，不执行临时拼接的 DELETE SQL。
