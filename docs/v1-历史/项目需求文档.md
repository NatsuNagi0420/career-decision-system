## 1. 文档目的

本文档用于统一产品定位、用户范围、Web 与 Android 分工、核心业务流程、功能优先级和验收标准，作为后续产品设计、界面重构、接口设计、数据库演进和测试验收的共同依据。

本文档描述的是“目标产品应当成为怎样”，不代表所有需求已经实现。现有代码应按以下状态理解：

- **复用**：现有能力基本符合目标，可以继续使用并完善。
- **重构**：现有能力可提供基础，但产品结构或交互方式需要调整。
- **新增**：当前缺少，需要后续开发。
- **后续**：不进入首个正式版本，先记录方向。

当本文档与早期 MVP 文档在产品流程上冲突时，以本文档作为新的产品方向基线；技术实现仍需遵守 `docs/ARCHITECTURE.md`、`docs/API_SPECIFICATION.md` 和 `docs/CODE_STANDARDS.md` 中仍然有效的工程约束。

## 2. 项目背景与问题定义

### 2.1 用户问题

大学生在职业规划中通常不是完全缺少信息，而是面临以下问题：

1. 不知道自己的经历、能力和偏好能够对应哪些职业方向。
2. 看过大量岗位和测评结果，但无法比较多个选项并做出决定。
3. 职业建议缺少真实招聘数据支撑，不知道结论为什么成立。
4. 得到报告后仍不知道今天、这周和这个月具体应该做什么。
5. 学习、项目、简历和投递彼此割裂，行动结果没有沉淀为新的能力证据。
6. 职业目标会变化，但传统测评和一次性报告无法随进展持续调整。

### 2.2 当前产品问题

当前产品主要围绕以下单向流程组织：

```text
信息录入 -> 能力画像 -> 岗位选择 -> 路径规划 -> 报告生成
```

这条流程能够生成结果，但存在三个核心缺口：

- “生成报告”被当作终点，而不是决策过程的自然产物。
- 用户完成路径规划后，缺少持续执行、证据记录和复盘调整。
- Web 与 Android 缺少明确分工，Android 容易变成 Web 功能的缩小复制版。

### 2.3 产品机会

产品应从“一次性职业测评和报告生成工具”升级为“证据驱动的职业决策与行动平台”，把个人经历、真实岗位、职业选择、行动任务和成长证据连接成闭环。

## 3. 产品定位

### 3.1 一句话定位

帮助方向模糊的大学生，基于个人证据和真实岗位数据，做出可解释的职业选择，并持续完成可验证的行动计划。

### 3.2 核心价值

产品必须同时提供以下四类价值：

1. **看清自己**：把经历、项目、技能、偏好和约束整理成有来源的个人证据。
2. **看懂职业**：通过真实招聘岗位理解职业要求，而不是只展示抽象职业标签。
3. **做出选择**：帮助用户比较候选方向，记录取舍依据、风险和待验证假设。
4. **持续行动**：把差距转化为任务，用成果证据和每周复盘持续修正计划。

### 3.3 产品原则

- 决策优先于报告，行动优先于分数。
- 真实证据优先于空泛评价，解释优先于神秘的“AI 匹配度”。
- MBTI 等测评只作为补充信息，不作为职业结论的唯一依据。
- AI 提供建议和解释，不替用户做不可逆决定。
- Web 负责深度思考，Android 负责日常执行。
- 后端是业务数据唯一可信来源，客户端本地数据只用于缓存和草稿。
- 不用虚构数据伪装成真实结果；示例内容必须明确标记为示例。

## 4. 产品目标与非目标

### 4.1 首个正式版本目标

首个正式版本需要让一名新用户完成以下闭环：

```text
建立个人档案
  -> 创建一个职业决策问题
  -> 获得并补充候选职业方向
  -> 使用真实岗位进行对比验证
  -> 确定主目标和备选目标
  -> 生成 4 周行动计划
  -> 在 Android 或 Web 完成任务并记录证据
  -> 完成每周复盘并调整计划
```

### 4.2 成功结果

用户完成核心流程后，至少应获得：

- 一个明确的职业决策问题。
- 2 至 5 个候选职业方向。
- 一个主目标和最多一个备选目标。
- 一份包含证据、风险和待验证事项的决策摘要。
- 一份默认 4 周、可调整的行动计划。
- 至少一个已完成并带有成果说明的行动任务。

### 4.3 暂不作为首版目标

- 不建设完整招聘投递平台。
- 不建设职业社区、内容广场或陌生人社交。
- 不建设导师撮合和付费咨询交易系统。
- 不建设院校管理后台和辅导员工作台。
- 不一次性增加大量心理或能力测评。
- 不让 Android 完整复制 Web 的复杂录入、岗位筛选和报告编辑。
- 不以多 Agent 数量作为创新点。
- 不在首版实现支付、会员和商业化计费。

## 5. 目标用户

### 5.1 核心用户

大二至大四、正在选择职业方向或准备求职，但对自身能力与岗位要求之间的关系缺少清晰认识的大学生。

典型特征：

- 有课程、项目、社团、实习等经历，但不会整理为职业证据。
- 在多个方向之间摇摆，例如开发、产品、数据、考研或考公。
- 会浏览招聘网站，但难以从岗位描述中提炼共性要求。
- 希望得到具体建议，又担心 AI 建议过于模板化。
- 容易制定很大的计划，但难以持续执行。

### 5.2 次要用户

已经有目标岗位，但需要分析能力差距、优化简历和制定求职行动计划的学生。

### 5.3 用户角色边界

首版只有学生用户。教师、辅导员、学校管理员和企业用户属于后续扩展角色，不进入首版权限模型和界面导航。

## 6. 核心业务闭环

### 6.1 闭环定义

```text
个人证据
  -> 候选职业
  -> 岗位验证
  -> 决策结论
  -> 行动计划
  -> 任务成果
  -> 每周复盘
  -> 更新个人证据或修正目标
```

### 6.2 核心业务对象

| 对象 | 说明 |
| --- | --- |
| 个人档案 | 用户相对稳定的教育、经历、技能、偏好和约束信息 |
| 个人证据 | 能够证明某项能力或偏好的项目、课程、实习、作品、反馈或测评结果 |
| 职业决策项目 | 用户围绕一个职业问题进行探索、比较和决策的工作空间 |
| 候选职业 | 决策项目中待比较的职业方向或目标岗位 |
| 岗位样本 | 用于验证职业要求的真实招聘岗位记录 |
| 决策证据 | 支持或反对某个候选方向的个人证据、岗位数据和实践反馈 |
| 目标职业 | 用户确认的主目标和可选备选目标 |
| 能力差距 | 当前证据与目标要求之间的差异及其可信程度 |
| 行动计划 | 围绕目标和差距生成的阶段性计划，首版默认 4 周 |
| 行动任务 | 可执行、可验收、可记录结果的最小行动单元 |
| 成果证据 | 任务完成后产生的文本说明、链接、文件或作品记录 |
| 每周复盘 | 用户对进展、困难、目标信心和下周安排的总结 |
| 决策报告 | 决策项目当前状态的可阅读快照，不是独立业务终点 |

### 6.3 决策项目状态

职业决策项目至少支持以下状态：

```text
草稿 -> 探索中 -> 已决策 -> 执行中 -> 已归档
```

首版同一用户可以保存多个项目，但工作台只突出一个“当前项目”。

## 7. Web 与 Android 产品分工

| 能力 | Web | Android |
| --- | --- | --- |
| 注册、登录和会话 | 完整支持 | 完整支持 |
| 个人档案深度编辑 | 主要入口 | 查看和轻量修改 |
| 测评 | 完整填写 | 首版仅查看结果 |
| 职业和岗位探索 | 完整搜索、筛选、详情、比较 | 查看已保存目标和岗位摘要 |
| 职业决策项目 | 创建、编辑、比较、确认决策 | 查看当前结论，进行轻量反馈 |
| 行动计划 | 创建、调整、全局查看 | 今日执行、打卡和记录成果 |
| AI 导师 | 页面上下文中的深度辅助 | 随时快速咨询和行动建议 |
| 报告 | 阅读、生成快照、导出 | 阅读简化版 |
| 每周复盘 | 完整复盘和调整 | 快速提交，复杂调整跳转 Web |
| 通知提醒 | 站内提醒 | 系统通知主入口 |

## 8. 目标信息架构

### 8.1 Web 一级导航

```text
工作台 | 职业探索 | 决策项目 | 行动计划
```

右上角用户菜单：

```text
个人档案 | 历史记录 | 设置 | 退出登录
```

导航规则：

- 一级导航表达用户要完成的事情，不表达系统内部处理步骤。
- 不在顶部同时展示“五步流程”和另一套同级功能导航。
- 能力画像属于个人档案与决策证据，不单独作为一级产品模块。
- 报告属于决策项目结果和历史记录，不单独作为流程终点。
- 岗位库整合进“职业探索”，避免把职业方向和招聘岗位混为一谈。

### 8.2 决策项目内部流程

```text
1. 明确问题
2. 整理证据
3. 收集候选
4. 对比验证
5. 确定目标
```

完成第五步后自动生成决策摘要，并引导用户创建行动计划。

### 8.3 Android 底部导航

```text
今日 | 目标 | AI 导师 | 我的
```

Android 启动后的默认页面必须是“今日”，而不是复杂功能总览。

## 9. 通用功能需求

### COM-001 注册、登录与会话

- 优先级：P0
- 当前状态：复用并完善

功能要求：

- 支持用户名、密码和可选邮箱注册。
- 支持登录、退出和会话恢复。
- Access Token 过期后使用 Refresh Token 进行单次轮换刷新。
- Web 与 Android 共享同一账号和后端数据。
- 登录失效时应保留未提交草稿，并明确提示用户重新登录。
- 不允许客户端直接保存明文密码。

验收标准：

- 用户在 Web 登录后可以正常完成受保护操作。
- 同一账号在 Android 登录后能看到 Web 已保存的目标和计划。
- Token 过期后能够自动刷新；刷新失败后回到登录页且不会无限重试。

### COM-002 新用户引导

- 优先级：P0
- 当前状态：新增

功能要求：

- 首次登录只收集完成首次决策所必需的信息，不强迫一次填完所有档案。
- 首次引导包含：当前年级、专业、毕业时间、当前困惑、已有方向、可投入时间。
- 用户可以跳过非必填项，后续由工作台和 AI 导师逐步提醒补充。
- 首次引导结束后直接创建或建议创建第一个职业决策项目。

验收标准：

- 新用户能够在 5 分钟内完成基础引导并进入工作台。
- 页面明确显示哪些字段必填、哪些可以稍后补充。

### COM-003 个人档案

- 优先级：P0
- 当前状态：重构

个人档案至少包含：

- 基础信息：学校、专业、年级、毕业时间、所在城市。
- 教育经历：课程、成绩亮点、证书。
- 项目经历：项目名称、角色、过程、结果、链接。
- 实习和实践：职责、成果、反馈。
- 技能：技能名称、熟练度、自评依据、最近使用时间。
- 职业偏好：行业、城市、工作方式、薪资关注、价值观。
- 现实约束：时间、地域、经济、家庭或继续深造计划。
- 测评结果：MBTI 等辅助信息及测评时间。

产品规则：

- 技能不应只有分数，应尽量关联可验证经历。
- AI 生成的标签必须标记为“AI 推断”，用户可以修改或删除。
- 画像结论应显示依据和更新时间。
- MBTI 结果不能直接决定推荐岗位。

### COM-004 草稿与跨端同步

- 优先级：P0
- 当前状态：部分复用、需要统一

功能要求：

- 关键表单应自动保存草稿，避免刷新或切换页面导致数据丢失。
- 已提交的业务数据以后端为准。
- 客户端本地仅保存会话、短期草稿和必要缓存。
- 同一账号在不同设备修改数据后，应展示最新更新时间。
- 发生冲突时不得静默覆盖，应提示用户刷新或选择版本。

## 10. Web 功能需求

### WEB-001 工作台

- 优先级：P0
- 当前状态：重构

工作台需要根据用户状态展示不同内容。

新用户状态：

- 显示欢迎信息和一个明确主操作：“开始第一次职业决策”。
- 显示基础档案完成情况，但不以大量百分比制造压力。
- 提供“导入简历”或“手动填写经历”两个入口。

探索中状态：

- 显示当前决策问题、当前步骤和下一项建议动作。
- 显示候选职业数量、已关联岗位样本数量和待验证问题。
- 显示最近一次 AI 建议，但不能替代主操作。

执行中状态：

- 显示当前目标、今日任务、本周进度和最近成果证据。
- 显示计划偏离、逾期或连续未行动等风险提醒。
- 提供进入完整行动计划和每周复盘的入口。

验收标准：

- 用户进入工作台后，可以在 10 秒内知道“当前目标、当前状态、下一步做什么”。
- 页面只能有一个视觉上最主要的下一步操作。
- 不展示与真实后端状态不一致的演示统计。

### WEB-002 职业探索

- 优先级：P0
- 当前状态：重构现有岗位探索

职业探索分为“职业方向”和“招聘岗位”两个层级。

职业方向要求：

- 展示方向简介、典型工作内容、常见能力、成长路径和常见误区。
- 支持按专业、行业、工作类型和兴趣进行浏览。
- 支持加入某个决策项目作为候选方向。
- AI 推荐方向必须说明推荐依据和信息缺口。

招聘岗位要求：

- 支持关键词、城市、行业、薪资和经验等筛选。
- 岗位详情展示来源、更新时间、公司、职责、要求和薪资信息。
- 支持收藏岗位、设为样本、设为目标岗位。
- 支持最多同时比较 3 个岗位。
- 对比内容至少包括技能、学历、经验、城市、薪资和职责关键词。
- 岗位匹配结论需要拆解为“已有证据、缺少证据、尚不确定”，不能只给一个总分。

验收标准：

- 用户可以从岗位列表进入详情，并将岗位关联到当前决策项目。
- 用户可以比较 2 至 3 个岗位，比较结果不会因字段为空而崩溃。
- 岗位来源和数据时间必须可见，过期数据应有提示。

### WEB-003 职业决策项目

- 优先级：P0
- 当前状态：新增核心模块，复用现有录入、画像、岗位和报告能力

#### WEB-003-1 明确问题

用户需要填写：

- 决策标题，例如“后端开发还是数据分析”。
- 希望在什么时间前做出决定。
- 当前背景和触发原因。
- 最看重的因素，例如兴趣、发展、收入、城市、稳定性。
- 必须满足的条件和不能接受的条件。

系统应帮助用户把过大的问题缩小。例如“我以后做什么”应被引导为“未来 3 个月优先验证哪两个方向”。

#### WEB-003-2 整理证据

- 自动引用个人档案中的项目、技能、经历、测评和约束。
- 用户可以新增、编辑、隐藏或标记证据可信度。
- 每条证据需要记录来源，来源可以是用户填写、测评、简历解析、任务成果或 AI 推断。
- AI 可以提示证据不足，但不能把推断伪装成事实。

#### WEB-003-3 收集候选

- 用户可以手动添加候选职业。
- AI 可以推荐候选，但首版总数控制在 2 至 5 个。
- 每个候选项显示推荐理由、不适合因素和待验证问题。
- 用户可以删除候选项，AI 不得自动重新添加用户明确排除的方向。

#### WEB-003-4 对比验证

- 支持以统一维度比较候选职业。
- 默认维度包括：兴趣与价值、已有证据、学习成本、岗位需求、地域机会、收入预期和风险。
- 每项结论必须关联证据或标记为“待验证”。
- 用户可以调整维度重要程度，但首版不要求复杂数学权重模型。
- 系统应推荐验证动作，例如分析 5 个岗位、完成一个微型项目、访谈一名从业者。

#### WEB-003-5 确定目标

- 用户选择一个主目标，并可选择一个备选目标。
- 用户需要确认选择理由、主要风险和下一次复查日期。
- AI 输出决策建议时必须同时展示支持理由、反对理由和不确定性。
- 用户确认后，系统生成决策摘要并引导创建行动计划。

验收标准：

- 用户可以保存草稿并继续上次进度。
- 用户不能在没有候选职业的情况下完成决策。
- 信息明显不足时，系统先提示补充或验证，不直接输出高置信结论。
- 完成项目后能够查看当时的证据、比较过程和最终选择。

### WEB-004 行动计划

- 优先级：P0
- 当前状态：重构现有路径规划

功能要求：

- 计划必须关联一个已确认或正在验证的职业目标。
- 首版默认生成 4 周计划，允许用户修改为 2 至 12 周。
- 计划按周组织，每周包含目标、任务和复盘。
- 任务字段至少包括：标题、类型、截止时间、预计耗时、验收标准、状态。
- 任务类型包括：了解职业、学习技能、完成项目、完善简历、建立联系、准备面试、投递实践。
- 用户可以新增、编辑、排序、延期、跳过和完成任务。
- 关键任务完成时应鼓励提交成果证据；没有成果的任务可标记为“已完成但未验证”。
- 计划调整应保留必要历史，避免用户看不到任务为何变化。

计划视图：

- “本周”视图用于执行。
- “全局”视图用于查看阶段和依赖关系。
- “成果”视图用于查看已沉淀的项目、链接和能力证据。

验收标准：

- 用户确认职业目标后可以生成一份非空计划。
- 每个 AI 生成任务都有具体动作和验收标准，不能只有“提高能力”一类空泛描述。
- Web 修改任务后，Android 应能看到最新任务。

### WEB-005 每周复盘

- 优先级：P0
- 当前状态：新增

复盘至少收集：

- 本周完成了什么。
- 产生了哪些成果证据。
- 遇到了什么困难。
- 下周可投入多少时间。
- 对当前目标的信心是提高、持平还是下降，以及原因。

系统根据复盘提出计划调整建议。任何删除、延期或新增任务的批量调整，都需要用户确认后写入。

### WEB-006 决策报告与历史记录

- 优先级：P1，基础查看属于 P0
- 当前状态：重构现有报告和归档

功能要求：

- 决策报告由项目数据自动生成，不再作为独立的第五个步骤。
- 报告包含问题、个人证据、候选比较、决策理由、风险、目标和行动计划。
- 报告标记生成时间和数据版本，后续更新项目不会悄悄改写旧快照。
- 支持查看历史快照；PDF 导出属于 P1。
- 简历分析、路径计划和职业报告统一进入历史记录，但按类型筛选。

### WEB-007 页面内 AI 导师

- 优先级：P0
- 当前状态：重构现有 AI 助手

功能要求：

- AI 导师应知道用户当前页面、当前项目、当前候选和当前目标。
- 在不同页面提供不同快捷问题，不做完全脱离业务上下文的聊天框。
- 回复优先采用“结论、依据、不确定性、下一步”结构。
- 引用用户档案或岗位数据时，用户能够知道引用了什么。
- AI 建议可以产生导航、添加候选、创建任务等操作，但写入数据前必须由用户确认。
- 聊天失败时展示可理解的原因和重试入口，不删除用户刚输入的内容。

## 11. Android 功能需求

### AND-001 Android 重构原则

- 优先级：P0
- 当前状态：保留网络和会话基础，重写主要界面与状态组织

保留范围：

- `RequestConfig.kt` 的统一后端地址设计。
- Retrofit API 接口和可复用数据模型。
- Android Keystore 加密会话存储。
- 登录刷新、错误归一化和已有单元测试思路。

重构范围：

- 拆分当前集中在 `MainActivity.kt` 中的页面、状态和业务逻辑。
- 建立清晰的页面、ViewModel、Repository 和网络层边界。
- Android 不再以“功能是否和 Web 一样多”为完成标准。

### AND-002 今日

- 优先级：P0
- 当前状态：新增核心首页

功能要求：

- 展示当前主目标和今日最重要任务。
- 默认只突出 1 个主任务，最多展示 3 个待办任务。
- 支持开始、完成、延期和跳过任务。
- 完成任务时可以填写成果说明和链接。
- 展示连续行动天数时不得制造惩罚感，断签后正常继续。
- 没有计划时，引导用户前往 Web 完成深度决策，或在手机上查看简化引导。
- 网络不可用时展示最近缓存，明确标记尚未同步的操作。

验收标准：

- 用户打开应用后，10 秒内能够开始今天的任务。
- 完成状态同步到后端后，Web 计划进度随之更新。

### AND-003 目标

- 优先级：P0
- 当前状态：重构现有报告、路径和岗位展示

功能要求：

- 展示当前主目标、备选目标和确认日期。
- 展示选择理由、主要风险、核心差距和计划进度。
- 展示已积累的成果证据。
- 支持提交“目标信心变化”快速反馈。
- 复杂的候选比较和目标修改引导至 Web，避免在小屏幕堆叠复杂表格。

### AND-004 AI 导师

- 优先级：P0
- 当前状态：重构

快捷场景：

- 今天先做什么。
- 当前任务卡住了怎么办。
- 解释一个岗位要求。
- 如何证明某项能力。
- 是否需要调整本周计划。

要求：

- 默认携带当前目标、今日任务和最近进展的最小必要上下文。
- AI 提出的任务变更必须由用户确认。
- 支持从回复快速跳转到今日任务或目标页面。

### AND-005 我的

- 优先级：P0
- 当前状态：重构

功能范围：

- 账号信息和退出登录。
- 个人档案摘要。
- 决策报告和历史记录入口。
- 通知设置、隐私说明和数据授权状态。
- 后端地址仅由构建配置决定，不在普通用户设置中暴露调试地址。

### AND-006 通知与提醒

- 优先级：P1
- 当前状态：新增

- 支持今日任务提醒、截止时间提醒和每周复盘提醒。
- 用户可以选择提醒时间、关闭某类提醒。
- 不以高频通知制造焦虑；同类提醒应合并。
- 点击通知能够进入对应任务或复盘页面。

## 12. Agent 功能需求

### 12.1 Agent 定位

首版采用一个受控职业决策 Agent，通过不同工作模式完成任务，不为了展示技术而拆成多个相互重复的 Agent。

工作模式包括：

| 模式 | 职责 |
| --- | --- |
| 决策教练 | 澄清问题、发现约束、组织候选和解释取舍 |
| 岗位分析师 | 提炼岗位要求、比较岗位样本、识别共性能力 |
| 行动教练 | 把能力差距拆成具体任务和验收标准 |
| 每周复盘助手 | 总结进展、识别阻碍并提出计划调整建议 |

### 12.2 上下文要求

- 客户端只访问后端，不能直接访问 Agent Server。
- 后端负责权限判断并组装完成任务所需的最小上下文。
- Agent Server 首版不直接访问业务数据库。
- 上下文应包括当前用户必要档案、当前决策项目、候选职业、岗位样本和行动计划。
- 不应把与当前任务无关的全部个人数据发送给模型供应商。

### 12.3 输出要求

- 业务输出必须是结构化数据，关键字段经过 Schema 校验。
- 推荐必须包含依据、反对因素、不确定性和建议验证动作。
- 任务必须包含动作、预计投入、截止建议和验收标准。
- 无法确认时明确表达不确定，不编造学校、企业或岗位事实。
- 岗位相关结论优先基于后端提供的真实岗位样本。
- 模型失败或输出不合法时，使用受控降级结果并提示用户结果可信度有限。

### 12.4 写操作规则

- AI 可以建议创建候选、确认目标、生成计划、调整任务。
- AI 不能在未确认的情况下删除候选、改变目标或批量修改任务。
- 每次 AI 业务调用保留 Trace ID、耗时、状态和脱敏后的审计信息。

### 12.5 AI 安全与表达

- 不承诺录取、就业、薪资或职业成功。
- 对薪资、市场趋势和岗位数量说明数据时间和适用范围。
- 避免以人格测试给用户贴固定标签。
- 表达应支持、具体、诚实，不制造“你不适合任何职业”等伤害性结论。
- 不在日志中记录原始简历、完整聊天、Token 或模型密钥。

## 13. 后端与数据需求

### 13.1 后端职责

- 账号、权限、会话和用户数据隔离。
- 个人档案、职业决策项目、候选、证据和目标持久化。
- 岗位搜索、收藏、样本关联和目标岗位管理。
- 行动计划、任务、成果证据和每周复盘持久化。
- 组装 Agent 上下文、调用 Agent、校验结果并记录审计。
- 为 Web 与 Android 提供一致业务接口。

### 13.2 目标数据模型

现有表可以复用或迁移，但目标模型需要覆盖以下能力：

- `decision_projects`：职业决策项目。
- `career_options`：候选职业及状态。
- `decision_evidence`：个人、岗位和验证证据。
- `decision_comparisons`：候选比较结论。
- `target_careers`：主目标、备选目标及决策理由。
- `action_plans`：行动计划，可从现有 `path_plans` 演进。
- `action_tasks`：行动任务，可从现有路径任务演进。
- `task_evidence`：任务成果证据。
- `weekly_reviews`：每周复盘和计划调整记录。
- `chat_sessions`、`chat_messages`：上下文对话记录。

最终表名由技术设计决定，但不能只把所有内容长期塞进一个不可查询的 JSON 快照。

### 13.3 接口规则

- 所有业务接口使用统一响应结构和 Trace ID。
- 所有用户私有资源必须由登录用户身份限定，不能信任客户端传入的用户 ID。
- 创建任务、提交复盘等写接口需要考虑重复点击和网络重试，避免生成重复数据。
- 列表接口需要分页、稳定排序和合理上限。
- AI 长耗时操作需要明确的处理中状态；P1 可演进为异步任务和进度查询。

## 14. 状态与异常体验

所有远程数据页面必须覆盖：

- 加载中。
- 正常数据。
- 空数据。
- 网络错误。
- 权限或登录失效。
- AI 生成超时或降级。
- 数据已被其他设备更新。

统一要求：

- 错误提示说明用户下一步可以做什么。
- 不因为接口失败清空已经填写的表单。
- 不连续弹出多条内容重复的错误消息。
- 生成过程超过 1 秒时展示明确进度状态。
- AI 超时后允许重试，并避免重复写入报告或计划。

## 15. 非功能需求

### 15.1 安全与隐私

- 局域网真机调试和生产通信均使用 HTTPS；Agent 仅在本机内部链路中使用受控地址。
- 密码必须采用安全哈希，Access Token 和 Refresh Token 不以明文持久化到后端数据库。
- Android 会话信息继续使用 Android Keystore 加密。
- `.env`、证书私钥、日志和本机配置不得提交到仓库。
- 用户上传简历或发送内容给外部模型前，应提供清晰的数据使用说明。
- P1 支持用户导出和删除个人数据；删除后相关私有记录不可继续被其他用户访问。

### 15.2 性能

- 普通页面进入后应尽快展示骨架或已有缓存，避免空白等待。
- 非 AI 普通接口在正常局域网和生产环境中的目标 P95 响应时间不超过 1.5 秒。
- AI 请求发起后 1 秒内显示生成状态，默认超时时间不超过配置上限。
- Web 首屏避免一次加载完整图表库和所有功能模块。
- Android “今日”页面优先加载任务，非关键历史数据延后加载。

### 15.3 兼容与可用性

- Web 支持常用桌面浏览器，并保证 360px 至 1440px 典型宽度下无关键内容重叠。
- Android 首版最低版本继续遵循现有工程配置。
- 表单支持键盘操作、清晰焦点和字段级错误提示。
- 不只依赖颜色表达成功、风险和状态。
- 用户可见文案以中文为主，术语保持一致。

### 15.4 可观测性

- Web、Android、后端和 Agent 共享请求 Trace ID。
- 后端记录接口错误类型和耗时，不记录密码、Token 和原始私密内容。
- Agent 记录模型、工作流、耗时、是否降级和错误类型。
- P1 建立基础运行监控和异常告警。

## 16. 数据指标与产品验证

### 16.1 北极星指标

**每周完成至少一项可验证职业行动的活跃用户数。**

“可验证职业行动”是指完成任务并填写成果说明，或关联作品、链接、文件等成果证据，而不是单纯打开应用或浏览报告。

### 16.2 核心漏斗

```text
完成新用户引导
  -> 创建决策项目
  -> 添加至少 2 个候选
  -> 关联岗位样本
  -> 确认职业目标
  -> 生成行动计划
  -> 完成首个任务
  -> 提交首次每周复盘
```

### 16.3 辅助指标

- 新用户完成基础引导的比例。
- 创建项目后 7 天内确认目标的比例。
- 生成计划后完成首个任务的比例。
- 带成果证据的任务占比。
- 7 日和 28 日行动留存率。
- AI 建议被采纳、修改和拒绝的比例。
- 用户对目标信心的变化。

### 16.4 首轮用户验证

- 访谈 10 至 15 名处于不同年级和专业的学生。
- 重点验证他们是否理解“决策项目”“个人证据”和“行动成果”。
- 观察用户是否能独立完成一次候选比较，而不只阅读 AI 结论。
- 记录用户完成第一次职业决策和第一次任务所需时间。
- 不以“用户觉得页面好看”作为唯一验证结果。

## 18. 首版端到端验收场景

使用以下场景作为产品和技术共同验收基线：

1. 一名大三学生注册并完成基础引导。
2. 用户创建“Java 后端还是数据分析”的决策项目。
3. 系统从个人档案提取已有项目和技能证据，用户完成修正。
4. 用户保留两个候选方向，并为每个方向关联真实岗位样本。
5. 系统展示两者的证据、差距、风险和待验证问题。
6. 用户选择 Java 后端为主目标、数据分析为备选，并确认理由。
7. 系统生成一份 4 周行动计划，其中任务具有截止时间和验收标准。
8. 用户在 Android “今日”完成一个项目任务并填写成果链接。
9. 用户回到 Web 后能够看到任务完成和成果证据同步。
10. 一周后用户提交复盘，AI 提出调整建议，用户确认后更新下周计划。

通过标准：

- 全程使用同一账号和同一套后端数据。
- 任一步骤失败后都能恢复，不丢失已填写内容。
- AI 结论能看到依据，不出现无来源的确定性职业判断。
- Web 和 Android 的功能分工清晰，不要求用户在手机上完成复杂比较。

## 19. 实施路线

### 阶段 0：产品基线与原型

- 确认本文档范围。
- 产出 Web 信息架构和关键页面低保真原型。
- 产出 Android 四个底部页面低保真原型。
- 完成首轮学生访谈，修正术语和流程。

完成条件：团队能够用同一套语言说明用户、问题、闭环和两端分工。

### 阶段 1：Web 决策闭环

- 重构一级导航和工作台。
- 建立职业决策项目。
- 整合个人档案、候选、岗位比较、目标和行动计划。
- 将报告改为自动结果和历史快照。

完成条件：用户只使用 Web 即可完成从新用户到行动计划的完整流程。

### 阶段 2：Android 行动端

- 保留现有网络和会话基础。
- 拆分 Android 工程结构。
- 实现今日、目标、AI 导师和我的。
- 打通任务完成、成果记录和跨端同步。

完成条件：用户可以在真机上完成每天的核心行动，不需要打开 Web 打卡。

### 阶段 3：Agent 质量提升

- 接入真实模型供应商。
- 完善四种工作模式和结构化输出。
- 建立固定评测案例，验证建议相关性、可解释性和安全性。
- 增加调用成本、降级率和响应时间监控。

完成条件：真实模型结果稳定优于固定模板，并能够在失败时安全降级。

### 阶段 4：试点验证

- 招募小规模学生试用。
- 观察核心漏斗和每周行动指标。
- 根据实际行为删减无价值功能，优化高频阻塞点。

完成条件：存在一批完成决策、执行任务并在下一周继续使用的真实用户。

## 20. 现有系统迁移原则

### Web

- 保留统一请求层、API 模块、类型、认证和可复用业务组件。
- 逐步重组页面，不要求一次删除所有旧页面。
- 当前“五步流程”过渡为决策项目内部流程。
- 先完成信息架构和关键流程，再进行大规模视觉美化。

### Android

- 不沿用单文件承载大量界面和业务逻辑的结构。
- 保留通信、会话、安全存储和测试资产。
- 以“每天回来执行一次”为核心重新组织页面。

### 后端

- 保留账号、岗位、测评、报告、简历、计划和 Agent 审计能力。
- 新增决策项目、证据和复盘领域模型。
- 数据库变更必须通过可重复、可追踪的迁移脚本管理。

### Agent Server

- 保留 FastAPI、LangGraph、Schema 校验、Trace ID 和降级机制。
- 将固定模板逐步替换为有真实上下文和岗位证据的模型能力。
- 不让 Agent 绕过后端直接读写数据库。

## 21. 创新创业展示主线

项目展示不以“功能数量多”为核心，而以一条清晰故事说明价值：

```text
学生不知道选什么
  -> 系统整理他的真实经历
  -> 使用真实岗位验证两个候选方向
  -> AI 解释为什么推荐、哪里还不确定
  -> 学生自己确认目标
  -> 系统生成可执行任务
  -> 手机持续记录行动成果
  -> 一周后根据真实进展调整计划
```

核心创新表述：

> 将学生个人经历、真实招聘岗位和持续行动记录连接起来，让职业规划从一次性测评报告变成可解释、可执行、可验证、可调整的长期决策过程。

潜在商业化方向可以保留为假设：个人增值服务、学校职业教育服务、就业指导数据工具。但在验证学生愿意持续行动之前，不优先开发支付和机构管理功能。

## 22. 待验证决策

以下问题需要通过用户访谈和试点验证，不应仅由开发人员凭感觉决定：

1. 核心用户是否进一步收窄到大三、大四求职学生。
2. 学生是否理解“个人证据”，还是更习惯“经历材料”等表达。
3. 默认 4 周计划是否合适，还是应根据毕业时间动态调整。
4. 用户是否愿意记录成果链接，哪些任务适合强制提供证据。
5. 职业方向与具体岗位应该如何建立稳定的数据映射。
6. 岗位数据来源、更新频率和展示授权是否满足长期使用要求。
7. 真实模型供应商、单次成本和用户隐私告知方案。
8. 创新创业比赛阶段优先证明用户价值，还是同时建设学校端演示能力。

在这些问题得到验证前，默认按本文档 P0 范围推进，不扩展新的大型功能模块。
