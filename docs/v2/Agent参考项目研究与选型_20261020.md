# Agent 参考项目研究与选型（2026-10-20）

本轮目标：扩大 OpenManus 以外的参考范围，并判断哪些设计能帮助青穗集完成画像、岗位分析、学习路线、练习和简历交付。用户随后提出本地安装配合 Web UI 的设想，因此补充本地与云端执行的区别。

研究范围是公开仓库元信息、官方文档、重点源码和许可证阅读。没有安装或执行上游项目，没有做真实模型对照实验；以下“适合参考”和优先级属于工程判断，不能视为已验收效果或迁移决定。

## 结论与建议

优先研究 DeerFlow 的完整任务应用结构、Deep Agents 的执行内核、Reactive Resume 的简历编辑交互，再参考 MyOfferAgent 的领域工具与事实保护、LibreChat 的本地部署与会话体验。AgentScope 是值得保留的另一套内核候选，不应与 Deep Agents 同时叠加。

先保留现有 React + FastAPI + LangGraph、账户、个人资料和成果层，以一条真实求职任务验证改进。换框架、换窗口或增加 Agent 数量，本身都不能形成求职产品差异。

## 当前项目基准

本地 README、server/pyproject.toml 及先前代码检查确认：当前项目使用 React、FastAPI、LangGraph、MySQL 与 SQLite checkpoint。开发时前后端在本机启动，模型可通过外部 API 调用。

`参考开源项目/README.md` 和其中部分能力笔记仍描述旧版 Spring Boot / Vue / Android / 本地 llama.cpp 方案。这些笔记可以用来定位上游源码，但其“如何整合”建议不能直接套用当前版本。本轮没有改写这些历史材料。

当前最需要验证的能力是：连续对话能否保持同一任务；能否理解上传材料并追问缺项；能否只修改指定段落；能否保留事实并交付可编辑、可导出的成果。这些能力与服务部署在本机还是云端分别设计。

### DeerFlow：最值得新增的完整应用参考

当前官方文档同时提供本机进程、Docker Compose 和更复杂的部署方案。部署文档列出网关、前端与本地访问入口；本地与容器执行并不要求先购买云电脑。

本轮阅读固定版本的主 Agent、线程状态和会话访问文件，重点关注同一会话的任务材料、工具过程和访问边界。对我们的参考价值在于把对话、执行过程和成果组织成工作空间。其较完整的服务体系也意味着整体迁入的评估成本较高。

该项目当前覆盖的范围已超过早期“深度研究”定位，应以此次固定版本的路径为准，不照搬旧教程的目录结构。没有在 Windows 上独立部署验证。

### Deep Agents：内核候选，需要验证接入成本

固定版本 graph.py 确认它基于 LangChain / LangGraph，装配文件、子 Agent、技能、上下文处理及人工确认等构件。入口允许传入模型、工具、checkpoint 等配置。它提供通用执行构件，求职资料、简历模板和岗位规则仍需我们提供。

项目当前直接使用 LangGraph，而 Deep Agents 同时带入 LangChain 及其依赖；因此“技术栈接近”不等于无成本替换。必须验证现有模型网关、事件流、审批与数据归属能否适配，不能默认复制示例即可完成升级。

### Reactive Resume：优先学习简历修改方式

工具合同提供 read_resume、read_attachment、ask_user_question 和 propose_edits 等能力。提案记录段落标识、修改前后、原因以及 pending / accepted / rejected 状态；会话 UI 包含接受、拒绝与撤销后的状态处理。另有独立的结构化文档补丁校验实现。

这些证据支持参考“简历是持续编辑的文档”这一交互：用户可以指着同一份简历说“改短一点”“突出这个项目”，系统产生可检查的局部改动。导出能力依据上游文档；我们没有实际生成文件测试排版与中文字体。

### MyOfferAgent：领域工具与事实保护

固定版本的 fabrication.ts 使用数字 token 对比，检查改写结果是否引入原文及上下文没有的数字。它比只写一句“不要编造”更可检查，但只是有限的数字保护：不能证明经历、角色、因果关系都真实，也不能识别已有数字被错误套用。

可以借鉴其结构化简历和领域工具分工；本地旧能力笔记中的 Spring Boot 整合步骤已经过时。本轮一次猜测的 resume 工具远程路径返回 404，记录保留为未核实；没有用该失败路径作为能力证据。

### LibreChat：验证本地 Web 形态可行

官方文档明确称其为自托管 Web 应用：在本机通过 Docker 或 npm 启动，再在浏览器访问。文档也明确，调用外部模型供应商时应用自身不运行模型，因此不要求 GPU；如自行运行模型，才需要为模型另算硬件资源。

它适合参考安装说明、会话与文件入口。将整个产品替换为通用聊天界面，会偏离现有穗奈陪伴和求职工作空间设想。

### AgentScope：保留为替代方案

官方文档与当前源码涵盖单 Agent 执行、工具、上下文、权限、事件和服务会话等构件，参考价值不限于多 Agent 编排。对我们有帮助的是运行过程和中断恢复如何组织，而不是复制 Agent 数量。

其服务体系与当前 FastAPI 业务服务的边界需要另做验证。现在没有证据证明整体迁入优于继续改进现有 LangGraph，故保留候选，不同时引入第二套执行内核。

## 本地 Web、桌面端与云端执行

“通过命令安装”描述分发方式；“Web UI”描述界面形式；“本地/云端”描述服务或工具在哪里执行。这些可以组合。

推荐先验证的形态：用户启动本机服务，通过浏览器与穗奈对话；任务工具读取用户选择的资料，生成简历和学习成果；模型理解与生成仍可以调用云端 API。

浏览器页面没有因显示为桌面样式就获得系统权限。读取指定资料、修改文件、浏览器自动化需要各自的工具和权限边界。本地服务可以承接这些工具；是否拥有能力取决于实际实现，安装到本地本身不会赋予能力。

本机运行不等于全离线，也不等于资料绝不外发：送入外部模型或搜索服务的内容仍会离开电脑。另一方面，云端 Web 应用也不意味着每个用户都有一台完整云电脑；普通服务、容器沙箱、远程浏览器是不同的基础设施选择。

本地执行的取舍是：我们减少托管任务执行环境的负担，用户承担安装、运行资源与电脑持续开机的条件。正式交付应处理环境检查、启动停止、版本更新、模型配置、错误提示和结果目录，不能要求普通用户理解目前的全部开发命令。

如果赛题要求可公开访问的网址、免安装体验或指定部署形式，应另核对交付规则。本轮没有取得完整规则，也没有认定本地 localhost 交付一定满足比赛要求。

## TypeScript Agent 的可行性与迁移边界

> 后续方向补充：用户进一步明确希望自研 TypeScript 执行底座，先在沙箱验证有限通用任务，再接入职业能力。新的拟实施路线见 `docs/agent-foundation/FOUNDATION_PLAN_20261020.md`；本节关于框架候选的内容保留为研究记录，不代表已选定 LangGraph TypeScript 或已开始迁移。

用户进一步提出用 TypeScript 构建 Agent、保留当前前端。本节记录选型判断和代码衔接依据；尚未新建运行时、安装依赖、切换服务或迁移数据。

### 判断依据

参考别人的 Agent 机制与选择同一种语言，不足以判断作品是否具有原创性。任务循环、工具注册、状态保存和人工确认可以学习；直接复用具体代码仍需核对许可证与声明要求。换一种语言也不能替代该核对。参赛时允许复用的范围和披露要求，以完整赛题规则为准，本轮没有据此宣称合规。

TypeScript 的合理收益是统一现有 React 前端与新增 Agent 的实现语言、便于共同维护接口与事件类型。这是工程选择，不保证模型更聪明、连续任务更可靠或产品自动形成差异。实际收益和迁移成本尚未通过运行对照验证。

### 现有前端可以保留的依据

- web/package.json 已使用 React、TypeScript 和 Vite。
- web/src/api/client.ts 集中处理 /api/v1 请求、Bearer 登录及任务事件流；UI 不直接依赖 Python 对象。
- web/src/state/frames.ts 负责事件合并、重放与界面状态；新后端应遵守现有帧含义，或通过明确适配转换。
- web/vite.config.ts 通过 VITE_BACKEND_ORIGIN 指定后端；开发接入新服务不要求重做全部页面。

因此可以保留大部分界面、穗奈素材、动画和交互。兼容条件包括路径、JSON 字段、鉴权、错误反馈、SSE 帧与 seq、成果和审批状态。新增连续会话、文档版本或文件选择能力时，仍可能调整接口和部分交互，不能承诺前端完全零改动。共享 TypeScript 类型也不能替代运行时输入校验和权限检查。

### 已核对的 TypeScript 候选

| 候选 | 官方文档确认的能力 | 对本项目的判断 |
| --- | --- | --- |
| LangGraph JavaScript/TypeScript | 持久执行、状态、流式事件、人工介入 | 优先做隔离验证；与现有 Python LangGraph 的概念接近，但业务实现和状态格式不能视为自动可迁移 |
| AI SDK | ToolLoopAgent、工具调用循环、停止条件、工具审批 | 适合评估较轻的工具循环；求职任务状态、文档版本和业务权限仍由我们设计 |
| Mastra | TypeScript Agent、工具、记忆、工作流 | 较完整的另一套候选；没有运行对照证据，暂不在现有系统上同时增加多套框架 |

在确认采用 TypeScript 的前提下，建议先比较现有基线与 LangGraph TypeScript 的一个小实现。此处的优先级是当前项目的适配判断，不代表它在所有场景优于其他候选。

目标结构可以是：

~~~text
现有 React + TypeScript 前端
    → Node.js + TypeScript 本机服务（接口、鉴权、事件）
        → 一套 Agent 执行内核
            → 求职领域工具（画像、岗位材料、学习计划、简历编辑与导出）
            → 外部模型接口
        → 业务数据、成果版本、任务记录
~~~

这是未来目标结构，不是当前已完成的架构。更换后端语言不改变模型可通过云端 API 调用的选择。

### 建议实施顺序与验收条件

1. 固定现有前端接口与事件含义，保留当前可用服务作为对照；不把页面重做与执行内核迁移混在同一轮。
2. 隔离实现一个 TypeScript 任务，从用户提供的简历文本及岗位描述开始，能追问、提出局部修改、接受反馈并生成可检查的成果。文档解析、中文排版和文件导出必须分别用真实材料验证，不能以模型声称完成代替文件。
3. 用同一份脱敏材料、同一个模型做对照：连续说“简短一点”“重点突出某个项目”时，应操作同一任务的最新成果；用户拒绝修改后，不应偷偷写入；工具报错和中断应显示真实状态。随后检查保存、重连与重复操作。
4. 第一条任务达标后，逐项迁移领域工具和必要服务；迁移期可以保留 Python 业务接口，但若目标是统一语言，应避免长期维护两套等价后端。

账号、业务记录、成果、审批和用户隔离都需要明确的兼容或迁移方案。当前 server/app/agent/service.py 创建 Run 时分配新的 thread_id，不能只改调用库就宣称连续会话已经解决。server/app/agent/checkpointer.py 使用 Python SQLite checkpoint，跨语言兼容性未验证；不能承诺直接复制后继续执行。切换前需处理活动任务与状态格式，再决定如何迁移。

最先验证的产品能力是“同一求职任务中的连续修改和真实成果”，不是框架数量、Agent 数量或语言差异。画像、岗位分析、学习路线与题目练习再围绕共享的用户资料和成果接入，避免各自生成互不衔接的报告。

## 下一步如何验证，而不是继续堆框架

保留现有程序作为基线，仅选择一个候选内核进行隔离验证；不同时引入 Deep Agents、AgentScope、Agno 和 Letta。

统一任务材料为一份脱敏经历和一个岗位 JD。让用户连续提出：整理画像与岗位差距 → 追问缺失信息 → 修改一段简历 → 改短一点 → 换一个突出重点 → 导出成果。比较同一模型下：

- 是否保持同一会话、材料与文档版本，理解连续修改的指代。
- 是否真实调用读取、修改和导出工具，成果能否打开、继续编辑。
- 是否保留来源事实，缺失成果数字时能否追问。
- 中断或工具报错后是否清楚反馈、能否继续。
- 用户操作步骤、成功率、总耗时、模型调用与 token 成本。

这些检查尚未执行；不能将上游展示效果当作本项目的验收结果。先证明一条任务可稳定完成，再决定扩大画像、岗位、学习与练习流程，或考虑独立桌面窗口包装。
