# P4 试点协议（10–15 名学生，两轮周复盘）

目的按目标原文：**用来发现问题，不是证明普遍有效**。所以这份协议里没有"平均分提高了"这种结论位，只有"哪一步流失、哪一步看不懂、有没有错误建议"。

现在就能全部跑通的部分都是**读已有数据**，不新增埋点；需要人配合的地方单独标了 🙋。写这份文档的时机是评测基线刚出（`AGENT_CAPABILITY_MAP.md` §32），模型侧质量有了可重复的门禁，剩下的未知全在人这一侧。

## 一、样本与周期

- 10–15 名在校大学生或毕业一年内，**专业/目标方向各不相同**（同专业的人凑一起，流失原因会被掩盖）。
- 周期 2 周：第 1 周走完"探索→比较→计划"，第 2 周提交至少一个任务结果并做一次周复盘。四周计划不需要跑完，跑不完本身就是数据。
- 🙋 每人一次 20 分钟出声思考（屏幕共享，边用边说），开局和结束各答一次前后测。**不要隔着问卷看它**——"是否理解证据与比较结果"这类问题，问卷问不出来，看着一个人点进"证据来源"才问得出来。

## 二、每项观察量用什么算

| 目标里列的观察 | 口径（现成数据） |
| --- | --- |
| 能否完成项目创建 | 注册账号数 → `decision_projects` 有行的账号数；分母里扣掉只注册没登录过的 |
| 能否建立 ≥2 候选 | `decision_candidates` 按 `project_id` 分组计数，≥2 记通过（`status` 全算，用户自己填的也算他做了决定） |
| 是否理解证据与比较结果 | 🙋 出声思考里两个任务：说出当前优先方向"为什么"，并指一条支撑它的证据；`GET /projects/{id}/comparison` 界面已给逐格引文，看人能不能自己找到 |
| 是否完成至少一个验证任务 | `task_results` 有行的任务数（>0 即通过），不看 `plan_tasks` 完成率——第一周完成率本来就该低 |
| 是否完成一次周复盘 | `weekly_reviews` 有行且 `run_id` 指回起草那一轮 |
| 使用后决策是否更清晰 | 前后测各一题：0–10「你现在知道自己下一步做什么吗」；只报分布和原文变化，不做显著性检验 |
| 行动是否更明确 | 前后测各一题：0–10「下周具体要做的事你能写出来吗」；再对一遍 `plan_tasks` 里的第一条任务，看他说的是不是系统真写了的那条 |
| 有无错误建议 / 过度信任 | 🙋 固定一问："有没有哪句你觉得它说得太肯定了？"，原文全录；同时看 `is_provisional=true` 的成果物有没有被用户复述成确定结论 |
| 哪一步流失最严重 | 每个账号最后一个有活动的 `capability_id` + 当时 `run.status`；`awaiting_approval` 后无动作单独算一类（那是确认门的问题，不是模型的问题） |
| 每完整用户模型成本 | 该用户全部 `agent_runs` 的 `prompt_tokens`/`completion_tokens`/`cached_tokens` 按 §28 峰时单价折算，再除以走完闭环的账号数 |

## 三、判读规则（先写下来，免得事后找解释）

- **任何一条"必须为 0"在试点里破功**（未审批写入、跨用户读取）→ 试点立刻停，先修再续。评测台架里是 0（§32），真用户环境更要防。
- 同一原因卡住 ≥3 人 → 算结构性缺陷，进 P2 队列，不当个案处理。
- 流失集中在"提交了结果之后" → 说明第 10–13 环节（结果→证据→复盘→重算）在人眼里没有回报，优先改的是那一段的可见反馈，不是模型。
- 超过 1/3 的人把临时结论说成确定结论 → 先查界面有没有把 `is_provisional` 演出来，再查模型；这条已有门禁指标（`uncertain_as_certain`）兜底。
- 样本 ≤15，一律用分布和原话汇报，不写百分比结论。

## 四、明确不做

不承诺 Offer、不自动投递、不代做决定；不给"适合度评分"这种会被当成结论的东西（目标二禁止把证据数量表达成适合度，试点期间最容易在这里破例）。

## 五、还欠什么

🙋 人。这份协议的数据口径全部可由现有表算出，成本换算按 §28 单价（峰时上限、USD 口径，账单币种未确认）。缺的是 10–15 个真实账号——需要你去招，我不能替你做这一步。

**2026-09-21 把上面那张表的口径逐列重核过一遍**（读 `app/db/models.py` 与 `app/db/domain.py` 的 `Mapped` 列，不是转述）：`decision_projects.user_id`、`decision_candidates.project_id`、`task_results.task_id`、`weekly_reviews.run_id`、`agent_runs.capability_id`/`status`/`prompt_tokens`/`completion_tokens`/`cached_tokens`、`artifacts.is_provisional` 全部在——所以"数据口径可算"这句现在是量过的，不再是断言。两处要防的读法：

- `RUN_STATUSES` 里 `running` 与 `paused` 只是词汇表（`app/` 内无处写入），因此流失判读**不能**把"停在 `running`"当成一种在飞状态；在飞的标记是 `created` + `finished_at IS NULL`。而 `awaiting_approval` **是**真状态（`app/agent/graph.py:749` 写），所以"确认门后无动作单独算一类"这句可算，且它是**人**停住的、不是模型停住的——`service.py:76` 的自动续跑名单故意排除它。
- 成本列里 `reasoning_tokens` 是 `completion_tokens` 的子集，折算时**不加**它（§26 实测三次），否则每个用户的钱会被高估一截。
