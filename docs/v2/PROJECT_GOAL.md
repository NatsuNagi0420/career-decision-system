# 职业决策 Agent v2 · 项目目标

> 本文件是需求取舍的判断依据。**不能直接帮助完成决策闭环、提高结论可信度或提升运行可靠性的工作，当前阶段原则上不进入 P0 与 P1。**

## 一、当前基线（2026-09-20，已按实测核对）

已经具备：

- 云端 OpenAI-compatible 模型已连通（当前 `deepseek-flash`），并保留 `mock` 离线档；
- React 19 + FastAPI + LangGraph 的 v2 单进程架构；
- 用户登录、外部 AI 授权（授权是服务端事实，客户端不存副本）、用户数据隔离；
- `Run` / `Step` / `Event` / `Artifact` / `Proposal` / `Approval` / `Obligation` 七类核心对象；
- 工具调用与 SSE 实时执行过程；结论正文与模型推理已做**瞬时流式通道**（不进耐久日志，不影响重放语义）；
- 写入前审批、事件持久化与断线按 `seq` 重放；
- 画像诊断、方向探索、决策框定、候选生成、证据收集、候选比较、行动计划等能力；
- MySQL 业务库（Alembic 单一迁移机制，当前 head 无漂移）+ SQLite LangGraph checkpoint；
- 门禁实测数字：`pytest` 84 通过、`vitest` 20 通过、`validate.py` 14 项通过、`ruff` 零告警、生产构建成功。统一入口 `scripts/verify.ps1`。

**结论：Agent 技术骨架验证已完成。下一阶段的目标不是增加技术概念，而是建设完整的用户价值闭环。**

一处必须写清的不等价：上面所有测试都跑在 `ScriptedProvider` 上，**没有任何一条断言真实模型的回答质量**。真实模型评测（目标五）目前为零。

## 二、总目标

> 把现有职业决策 Agent 技术原型，建设成一个可供真实大学生与初入职场者使用的、证据驱动的职业决策闭环 MVP。

用户从一个模糊的职业困惑出发，Agent 在授权与代码约束内自主读取职业画像、职业方向、真实岗位样本、候选方案与历史证据，完成决策问题整理、候选方向生成、证据缺口识别、多标准比较与行动计划制定。

**在用户完成验证任务并提交结果后，Agent 应继续整理新证据、完成周期复盘、更新原有判断并生成下一阶段行动，而不是在生成一份报告后结束。**

系统最终需要保证：

| 保证 | 当前状态 |
| --- | --- |
| 重要结论能回溯到证据 | 已实现（逐字引文 + `source_refs` + 覆盖度由代码计算） |
| 证据不足时明确表达不确定 | 已实现（`is_provisional` + `uncertainties` + 扣住写入） |
| 重要业务写入必须经用户确认 | 已实现（Proposal + Approval，R2/R3 强制） |
| 执行过程可查看、可恢复、可审计 | 部分（事件流与 checkpoint 已有；服务重启后的 Run 恢复未做） |
| 用户可以拒绝、修正或终止建议 | 已实现（批准/拒绝/反馈、承诺可放弃） |
| Agent 跨会话记住承诺的下一步 | 已实现（`Obligation` + 冷却只约束系统自发运行） |
| 模型与工具失败不伪装成成功 | 部分（网关有截断与 schema 护栏；评测未建基线） |
| 调用质量与成本可评估 | **未实现**（有 token 记录，无评测门禁） |

## 三、要解决的核心用户问题

不以"给用户推荐一个职业"为目标，而是解决这个**过程性**问题：

> 当用户在多个职业方向之间犹豫时，如何帮助他基于个人经历和真实岗位证据，逐步缩小选择范围，识别未知信息，通过实际行动验证假设，并形成一份当前阶段可执行、可解释、可被新证据修正的职业判断。

典型输入："我在数据分析师和后端工程师之间犹豫，不知道自己更适合哪个方向。"

系统不能只输出一段分析，而应逐步交付：结构化决策问题 → 2–3 个候选方向 → 每个方向的真实岗位要求 → 个人经历与要求的对应关系 → 已有证据 → 仍无法判断的关键问题 → 验证用行动计划 → 行动产生的新证据 → 更新后的比较 → 当前优先方向 → 未解决的风险与下一步。

最终形态不是"AI 替用户决定一生的职业"，而是：

```text
当前优先方向 + 支持证据 + 反对证据 + 尚未确认的风险 + 下一步验证计划
```

## 四、本版本必须形成的闭环

```text
用户提出职业困惑 → 职业画像诊断 → 整理为决策项目 → 生成/补充候选方向
→ 读取真实岗位样本与要求 → 识别已有证据与缺口 → 多标准比较
→ 制定四周验证行动计划 → 用户执行任务并提交结果 → 结果整理为新证据
→ 每周复盘 → 更新比较结论与不确定项 → 生成下一周期行动计划
```

第 1–9 环节已完成（2026-09-20 补上"用户执行任务并提交结果"，记录见 `AGENT_CAPABILITY_MAP.md` §19）。**本阶段最重要的工作是补齐后四个环节**：结果转化为证据、每周复盘、比较结果更新、下一周期计划生成。只有这部分完成，项目才从"能生成职业分析"升级为"能持续推进职业决策"。

2026-09-20 实测了一件事，它把后五个环节的性质改写了：**表已经建好，但没有人写它们**。`task_results`、`comparison_criteria`、`comparison_results`、`weekly_reviews` 四张表在 `app/` 里的引用数分别是 **0 / 0 / 0 / 1**（那 1 处只是能力注册表里一个 `status="planned"` 的名字），而 `evidence_items` 已经有 10 处读写。（2026-09-20 更新：`task_results` 已经接上读写——提交、幂等、唤醒 run、工具可读、feed 可列；剩下三张仍是死的。）同时 `is_valid_obligation_target()` 只接受 `implemented` 能力，所以 `action_plan` 永远无法承诺周复盘——指向它的承诺被静默丢弃。

这意味着 P1 不是"设计并新建一套复盘功能"，而是**给已有的死表接上动词**，且必须按依赖顺序：先让用户能提交结果（用户自己的动作，走鉴权 REST 而不是 Proposal），再让 Agent 把结果归档成证据（`EvidenceItem.quote` 存用户原话，R2 需审批），然后才可能把 `weekly_review` 转成 `implemented`（R3：模型起草、人终局确认），最后带新证据重算比较并建立成果物版本链（`Artifact.version` 是乐观锁计数，不是逻辑版本，版本链需另加自引用列）。

## 五、可验收目标

### 目标一 完成一次真实的职业决策闭环

用户能从困惑出发走完 `探索 → 比较 → 验证 → 行动 → 反馈 → 复盘 → 调整`。

验收：可创建决策项目；一个项目支持 ≥2 个候选方向；候选可关联真实岗位样本与要求；系统指出比较依据与缺失证据；Agent 生成具体可执行的验证任务；用户可提交任务结果；结果可归档为证据；新证据能影响后续比较；Agent 生成周复盘与下一步计划；用户能看懂结论为什么变化。

### 目标二 结论可追溯

不靠"要求模型别幻觉"，而靠数据结构与程序约束让结果可检查。

验收：所有要求证据的 Artifact 带来源引用；关键结论对应到岗位原句、用户事实或任务结果；找不到证据必须标记为临时结论；不允许用模型常识冒充项目数据；**不允许把"证据数量"直接表达为"职业适合度"**；比较矩阵分别呈现支持/反对/缺失证据；用户可查看来源而不只看到分数。

### 目标三 重要写入可控

以下操作必须经过 Proposal + Approval：新建决策项目、新增候选职业、写入画像事实、归档职业证据、创建行动计划或任务、修改重要项目状态。

同时：用户可批准/拒绝/补充反馈；重复点击批准不重复写入；已过期审批不能执行；执行失败时审批状态不得显示成功；Agent 不得自动确认用户唯一职业目标；删除与终局确认不得由 Agent 自动执行。

### 目标四 任务具备可靠生命周期

模型连通后，主要工程风险不再是"能否拿到回答"，而是任务能否稳定运行。

验收：刷新页面能恢复当前 Run；SSE 断线从最后 `seq` 续传；不产生重复事件或重复写入；服务重启后不允许 Run 永久停在 `running`；未完成任务要么可恢复要么明确失败并可重试；审批超时被实际执行而非只存在于代码；用户可取消未执行的后续承诺；每次 Run 有最大步骤数、token 预算与超时；模型/工具/数据库失败时能显示具体失败阶段。

### 目标五 真实云端模型评测

建立 ≥30 条固定评测案例，覆盖：画像信息不足、两方向比较、多候选生成、岗位样本查询、证据不足、用户事实与岗位要求冲突、行动计划生成、用户拒绝提案、模型工具参数错误、模型试图调用未授权工具、模型生成无效 Proposal、用户未授予外部 AI 权限。

指标基线（首次真实评测后可调整，但必须先有可重复执行的基线）：结构化结果最终生成成功率 ≥90%；需证据成果物具备有效来源比例 ≥95%；未经审批的业务写入次数 **=0**；跨用户数据访问次数 **=0**；未知事实被表达为确定事实的比例 ≤5%；模型失败不得产生虚假成功 Artifact；每能力可统计平均调用次数、token 与费用。

## 六、优先级

**P0 工程与项目定义收口**（继续开发的前提）：v2 定为唯一主线；更新根 README 与启动文档；清理旧 Vue / Spring Boot / Android / 旧 Agent 描述；清理前端重复的 JS 与 TS 产物；整理未提交文件；统一数据库迁移方式；建立一条可重复执行的完整验证命令；确保文档、代码与实际启动方式一致。
完成判据：任何开发者照 README 能启动系统并准确理解当前架构。
✅ **2026-09-20 已完成**：八项逐条落地，`scripts/verify.ps1` 七项门禁全绿。判据当场不成立的那一条（全新库上 `alembic upgrade head` 死在 MySQL 1049 Unknown database）已修在代码里——迁移前按 `^career_v2[A-Za-z0-9_]*$` 自动建库，实测探针库从零建起并跑完 6 个 revision。过程记录见 `AGENT_CAPABILITY_MAP.md` §18。

**P1 补齐决策闭环**：任务结果提交 → 结果证据化 → 每周复盘能力 → 比较矩阵重算 → 依新证据更新结论 → 下一周任务生成 → Artifact 版本关系 → 用户对复盘结果的确认。
完成判据：一个用户能真正完成一次"计划—行动—复盘—调整"。
✅ **2026-09-20 第 1 项「任务结果提交」已完成**：`POST /api/v1/tasks/{id}/results`（原样存用户的话、`request_id` 幂等、越权 404）+ 前端"行动清单"，提交即唤醒 `evidence_collect` run。真模型 + 浏览器实测：提交后 run 自己起来跑完 8 步并给出 R2 归档提案。第 2–8 项按依赖顺序待做。

**P2 提高运行可靠性**：同步 DB 操作阻塞事件循环；进程内后台任务中断；服务重启后的 Run 恢复；审批超时调度；Run 取消与重试；事件并发序号安全；多标签页重复操作；模型调用超时与成本预算；运行日志与错误监控。
完成判据：不再只适合单用户本地演示，可支撑小规模真实试点。

**P3 真实模型质量建设**：固定评测集；工具调用正确率；证据引用质量；不确定性表达；虚构信息检测；模型输出修复；不同模型效果与成本对比；长上下文裁剪；Prompt 与 Capability 版本管理。
完成判据：改 Prompt / 工具 / 模型后能判断质量是升是降，而不依赖主观体验。

**P4 真实用户试点**：10–15 名学生，用于发现问题而非证明普遍有效。观察：能否完成项目创建、能否建立 ≥2 候选、是否理解证据与比较结果、是否完成至少一个验证任务与一次周复盘、使用后决策是否更清晰、行动是否更明确、有无错误建议或过度信任、哪一步流失最严重、每完整用户模型成本。

## 七、本阶段明确不做

不做通用型万能 Agent；不自动替用户决定唯一职业；不自动投递简历；不自动操作招聘网站；不承诺帮助拿到 Offer；本阶段不恢复 Android 客户端；不优先扩展复杂多模型编排；不优先增加大量职业测评；不优先做简历/JD/面试的完整功能；不在闭环完成前继续堆叠页面。

简历生成、JD 匹配、面试准备可作为下一阶段能力，但不得抢占闭环建设优先级。

## 八、完成定义

不以"接口写完"或"页面做完"为标准。同时满足才算完成：

1. 真实用户可独立走完职业决策闭环；
2. Agent 使用真实云端模型与真实工具数据；
3. 所有关键结论可回溯到证据；
4. 证据不足时不伪装成确定结论；
5. 所有关键写入都经用户批准；
6. 刷新与重连不丢失 Run；
7. 服务异常不会让任务永久卡住；
8. 行动结果能改变后续判断；
9. 真实模型评测达到设定门槛；
10. 至少完成一轮小规模真实学生试点。

## 九、正式目标文本

> 本项目下一阶段的目标，是将当前已接通云端模型并具备 Agent 运行、工具调用、成果物、提案审批、事件流和跨会话承诺能力的 v2 原型，建设成一个可以供真实学生使用的证据驱动型职业决策闭环 MVP。系统应帮助用户从模糊职业困惑出发，完成职业画像诊断、方向探索、决策问题框定、候选职业生成、真实岗位证据收集、多标准比较和行动计划制定；在用户完成验证任务后，继续归档行动结果、生成周期复盘、更新比较结论并制定下一阶段计划。所有关键结论必须能够回溯到用户事实、岗位样本或行动证据，证据不足时必须明确标记为临时判断；所有重要业务写入必须经过用户确认。项目还需要解决任务恢复、审批超时、重复写入、模型失败、运行成本和真实模型评测等问题，最终通过小规模学生试点验证系统是否能够提升用户的职业决策清晰度和行动能力。

**一句话开发目标**

> 把当前"能够运行的职业 Agent 原型"，做成一个能陪用户完成一次真实的"探索—比较—行动—复盘—调整"职业决策闭环，并且结论有证据、写入可确认、任务可恢复的试点级产品。
