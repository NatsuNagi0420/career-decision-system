# 界面方向：搬《主播女孩重度依赖》的机制，不搬它的情绪

> 结论先行：这不是一次"换个像素皮肤"。参照对象值得抄的是**把"关系"做成可操作界面**的五个机制（桌面即界面、有限回合、角落数值板、单条裁决、多版本回看）；不值得抄的是它的数值语义（压力/好感/精神值）和结局语义（22 个结局）。
>
> 我们的情绪引擎必须反着转：**它靠消耗留住玩家，我们靠积累留住用户。**

- 状态：方向稿（S6 系列的第一份）。未改动任何生产代码。
- 依据：本文所有"现在有什么"都来自读码与实测，数字写在各节里；外部事实只引一处并在 §7 注明。
- 配图：
  - 现状：`docs/v2/ui-direction-prototype/current-desktop.png`（2026-10 真机首屏，由 `npm run verify:e2e` 截）
  - 方向草图：`docs/v2/ui-direction-prototype/desktop.png`（1440×900，源文件 `desktop.html`，自包含可离线打开）

## 1. 先量了三件事，它们决定了方案长什么样

**① 桌面壳已经做出来了，所以问题不是"要不要做桌面"。**

`web/src/components/DesktopScene.tsx` + `web/src/desktop.css`（27.2 KB）已经是一个完整桌面：masthead、左栏五个应用图标、穗奈小窗、便签、成果窗口、底部任务栏（含"开始"按钮）。配套还有：自托管的 Fusion Pixel 像素字体（650 KB woff2，OFL）、`PixelIcon`、以及 `web/src/character/suinai.ts` 里一份**代码画的**像素稿——80×96 网格、8 种表情、6 种姿势、8fps、48 帧循环、两套渲染模式（方块/点阵）。

那份文件里已经有一条我们自己的纪律，值得原样继承：

```ts
// A happy face is not evidence that anything was saved. Filing is explicit only.
```

**② 它现在长这样（真机跑的，不是示意图）**：`web/e2e/.shots/empty-desktop.png`。左栏五个应用、中间"穗奈消息"窗口、右栏穗奈小窗（像素稿 + 点阵切换）、底部任务栏——桌面这一层已经是完整的。

但同一轮实测也抓到：`npm run verify:e2e` 现在是 **30/34**，红四条，且都不是"新功能没做"，而是改壳时撞红了既有守卫：

| 红的检查 | 实测值 | 原因 |
|---|---|---|
| `the field drifts while she is idle` | `x nonepx → nonepx` | `desktop.css` 里 `.app > .field { display: none; }` 把麦浪整块关掉了（§54 那三条正弦白做了） |
| `the composer rim travels` | `rotate none → none` | 输入框流动光效在桌面壳里没有生效 |
| `login talks about job seeking`（桌面 + 手机各一条） | `打开你的成长桌面` | 登录页 CTA 不再提求职，与 §49 建立的 C 端用词契约不一致 |

**③ 而且这版桌面主题活在契约之外。**

`styles.css` 的色板有 `palette.contract.test.ts` 守着（≥60° 色相分离、无零饱和白、正文对比度 ≥4.5），圆角有 `styles.contract.test.ts` 守着（只能来自五个令牌）。**两个契约都只 `readFileSync("./styles.css")`。**

实测 `desktop.css`：186 个唯一色值，**全部硬编码、零令牌引用**；其中 136 个（73%）落在 240–300° 紫/蓝紫色相带（240–269° 54 个、270–299° 82 个）。这不是审美判断，是"现值 vs 守卫覆盖范围"的差：

| | styles.css | desktop.css |
|---|---|---|
| 唯一色值 | 由 `--md-*` 令牌构成 | 186 个裸十六进制 |
| 色相落点（按唯一色值计） | 契约强制 ≥2 个色相族 | 73% 在紫带 |
| 被契约测试读过 | 是（2 个文件） | **否** |
| 圆角 | 五名令牌表 | 直接用 `var(--r-sm)` 等（这部分是对的） |

结论：**S6 的第一片不是加功能，是把这 186 个色收成令牌，并把两个契约扩到 `desktop.css` / `character.css`。** 否则后面每一笔视觉改动都没有东西能判它对错——这正是 §45/§47 已经吃过一次的亏。

**③ 参照对象的机制，和我们已有的对象几乎一一对得上。**

§7 列了外部依据。逐条对下来，NSO 的六个机制里我们已经具备五个半，唯一真的缺的是**数值板**和**多版本回看**这两块界面。

## 2. 机制映射（抄机制，不抄皮）

| 《主播女孩重度依赖》的机制 | 它解决的用户问题 | 我们已经有的 | 还缺什么 |
|---|---|---|---|
| 整个产品就是一台假桌面，人物住在你的电脑里 | 陪伴感来自"她在"，不来自大页面 | `DesktopScene` + 任务栏 + 小窗 | 桌面图标没有"待办/未读"角标；窗口没有"最小化但还在跑" |
| 一天切成 noon/dusk/evening，每个行动占时段 | 有节奏，不会无限拖 | 闭环 13 环节、4 周行动计划、`weekly_review` | 没有"这一周走到第几天/第几周"的可见位；`LoopSpine` 五格是流程不是回合 |
| 右上角 Task Manager 常驻四项数值 | 随时知道"现在什么状态" | 真实数字全都有（`data_coverage`、`source_refs`、`uncertainties`、`Obligation`、pending `Approval`、`TaskResult`） | **没有任何一块界面把它们并排放在一起** |
| JINE 手机聊天窗 | 对话不必占据整屏 | 消息流 + 确认门 + 流式正文 | 对话和成果仍是两个"页面"，不是一个桌面里的两个窗 |
| 直播时逐条裁决弹幕（删/推） | 高互动来自"一条一条做小决定" | 审批卡（一次一批） | **没有"一次只问一条"的粒度** |
| 22 个结局 + 可回看怎么走到 | 选择有后果感 | `Artifact.supersedes_id` 版本链、`comparison_results.round_no` 逐轮追加、`GET /projects/{id}/comparison` | 界面上没有"版本回看"，用户看不到"这一版相对上一版哪几格变了" |

## 3. 必须反转的三件事（这是本方案的核心，不是修饰）

**① 数值从"人"挪到"决策"。**

NSO 的四项数值是**她的状态**（粉丝/压力/好感/精神值），玩家在看一个人被消耗。我们如果照抄，就会得到"穗奈好感度"，直接撞上两条既有红线：品牌禁区（不把 AI 做成偶像/依赖对象）和 `PROJECT_GOAL` 的"不允许把证据数量表达为职业适合度"。

所以面板上只允许四类**过程量**，每一格都必须能点开看到出处：

| 格子 | 数据来源 | 为什么不许换成百分比 |
|---|---|---|
| 能对上的原话 `7 / 9` | 成果物 `source_refs` 逐字比对 | 它不是置信度，是两个整数 |
| 还没答上的问题 `3` | `uncertainties` 条数 | 数得清，且每条都能念出来 |
| 等你点头的卡 `1` | pending `Approval` | 这是要他做事的提醒，不是分数 |
| 这周该做还没做 `2` | 任务 + `Obligation` | 过期不消失，变成欠着的事 |

**② 情绪引擎从"消耗"改成"积累"：22 个结局 → 一条版本链。**

NSO 的结局是惩罚性的（看她坏掉）。我们是学生场景 + 省级课题，任何"你选错了"的结算都可能造成伤害，而且与"不替用户决定"冲突。

替代物已经有了数据基础：`artifacts.supersedes_id` 是真链条、`comparison_results.round_no` 是真轮次。所以界面语言是**"你走到了第 3 版"**，配一句"相对 v2，有 2 格判定变了"。不是结局，是可回看的草稿史。

**③ 双人格（Ame / KAngel）→ 两个声音（穗奈说的 / 系统核实的）。**

这是整套映射里最值钱的一条，因为**项目已经在数据层做完了**：§36 拆掉了两处"看起来有出处"的假话，§43 把界面上的"来源"从模型自述换成系统绑定的行指针，`frames.ts` 的 `rowPointers/pointerSummary` 会把 `agent_runs`/`tool` 记账剔掉、认不出的表保留表名。

而界面上现在只体现为一行小字。NSO 的双人格是"表层/真实"的张力；我们的版本是"**她说的**"与"**代码核实的**"并置。这既是视觉张力，也是这个产品唯一真正的卖点：不要求模型不说谎，而是让用户一眼看出哪句是模型说的。

## 4. 六片改造（S6-1 … S6-6）

每片都写清"改什么 / 判据 / 能红的守卫"。顺序不能换：前两片是后四片的地基。

### S6-0 先把四条红修回来（半天，必须先做）
`verify:e2e` 30/34 不是"验收标准太严"，是**桌面壳把既有行为撞坏了**：麦浪被 `display:none` 关掉、输入框光效没接上、登录页 CTA 丢了求职词。
- 改法：`desktop.css` 不隐藏 `.field`（要么缩到窗口后面，要么换成窗口内的低对比底纹），输入框动效沿用 `styles.css` 的那套而不是重写，登录页 CTA 回到 §49 的用词表。
- 判据：`verify:e2e` 回到 34/34。
- 守卫：这四条本来就是守卫；不许为了绿灯删断言（§46 那种"数值全绿但被眼睛否掉"的反面教材已经有过一次）。

### S6-1 令牌收口（前置，不做完不许动视觉）
- 把 `desktop.css` 的 186 个色值与 `character.css` 的 3 个，收成 `--dt-*`（桌面）令牌表，落在 `styles.css` 或新增的 `desktop.tokens.css` 里。
- `palette.contract.test.ts` / `styles.contract.test.ts` 的扫描范围改成**读全部 CSS 文件**（不是只读 `styles.css`）。
- 判据：全站裸十六进制数 = 0（除 `#fff`/`transparent` 之类在令牌文件内的定义）；桌面主题的两个色相族间距 ≥60°；正文对比度 ≥4.5。
- 守卫：负向验证——塞回一个裸紫色，测试必须红；守卫要自证"数到了 186 个"（沿用 §47 那条"守卫必须自证数到了东西"）。

### S6-2 过程账本（最高收益，纯只读）
- 右栏常驻四格（§3①），每格点击展开出处行（复用 `EvidenceDrawer` + `rowPointers`）。
- 判据：四格的数字必须来自后端已存在的字段，前端不许自己算"覆盖率"；点开必须看到至少一行 `table+id`；没有数据时写"还没测到"，不写 0%。
- 守卫：一条扫字符串字面量的契约（沿用 §49 的 copy 契约）禁止"适合度/匹配度/录取概率/推荐指数"出现在任何组件里。

### S6-3 周回合与周结算
- 任务栏加"第 3 / 4 周"进度；`weekly_review` 从卡片升级为**结算屏**：这一周做了什么、交回几条结果、哪一格判定变了、下一周 4 件事。
- 判据：结算屏每个数字都能点回 `task_results` / `evidence_items` / `comparison_results` 的行；不许出现"完成度 70%"这类无分母分数。
- 守卫：拿掉 `run_id` 绑定 → 结算屏必须显示"这一周没有可核对的记录"而不是空表。

### S6-4 单条裁决（交互性最强，也最贵）
- `Approval` 从"一次一批"派生"一次一条"的审阅流：一条引文 + 两个按钮（对得上 / 对不上）+ 一句"裁决只记归属，不动分数"。
- 写回：裁决结果进 `comparison_results.counter_refs`（反对证据）与 `EvidenceItem`，**不新增写入路径**，仍走 Proposal+Approval。
- 判据：一次只出一条；键盘可完成；「对不上」不得降低任何分数，只能新增一条反对证据。
- 守卫：一条测试断言"驳回一条证据后，同一格的支持证据数不变、反对证据 +1"。

### S6-5 版本链回看
- "这一版结论"卡片：`v3 ← v2 ← v1`，点开看逐格差分（复用 `GET /projects/{id}/comparison`）。
- 判据：差分只显示"判定变了"的格，不显示"总分"；每格给出双方原话。
- 守卫：只有 `status=committed` 的矩阵能进链条（§42 已修，界面要跟着走）。

### S6-6 表情可归因
- 现在 `face` 只有三态（`awaiting→listen`、`running→think`、否则 `smile`）。扩到 8 表情时，每一态都必须有**数据来源**，且界面上写明来源（草图上那行"表情来源：run #4821 · step 4"）。
- 判据：表情由真实字段决定，不由"对话气氛"决定；无来源时退回 `smile`。
- 守卫：把来源字段置空 → 组件必须退回默认表情而不是保留上一个表情。

## 5. 三条要写进契约的硬规则

1. **表情必须可归因。** 没有来源字段的表情一律不许出现（继承 `poseForFace` 那条注释的精神：开心不等于已保存）。
2. **状态板不许出现适配度。** 只许整数计数与"测到/没测到"，不许百分比形式的"匹配"。
3. **桌面壳的颜色只能来自令牌表。** 这就是 S6-1，但要写进契约而不是靠自觉。

## 6. 明确不照搬的四件事

1. **不复刻 Windows 95 的具体外观，也不用它的专名。** 95 风是一种通用语汇，但它的具体贴图、假应用名（JINE / Tweeter）、角色（Ame / KAngel）都是别人的。我们用自己的语汇：手账、索引标签、麦穗、纸质窗口标题条——这些在 `docs/穗奈角色设定与品牌视觉生成稿.md` §4.4 已经定为品牌锚点。
2. **不做好感度 / 依赖度。** 与品牌禁区冲突，且会主动制造"过度信任"——那正是 P3 评测里明确要防的失效模式。
3. **不做惩罚性结局。** 见 §3②。
4. **不做沉默的自动化。** NSO 的玩家是旁观者，我们的用户是当事人。任何自动动作（自动开工、自动归档、自动重排计划）都要在桌面上留一行"我打算做什么，依据是哪一行"。

## 7. 外部依据（只此一处）

参照对象的机制描述取自英文维基百科 *Needy Streamer Overload* 的 Gameplay 一节（2026-10 抓取，`https://en.wikipedia.org/wiki/NEEDY_STREAMER_OVERLOAD`）：pastel 系 Windows 95 风界面；桌面图标选每日行动；一天分 noon/dusk/evening 三个时段；Task Manager 常驻粉丝数、压力、好感、精神值；JINE 即时通讯；直播时段可逐条删除/推广弹幕；Tweeter 上可窥见角色心情；发售时 22 个结局（2022-10-28 更新又加了）；目标是"一个月内 100 万粉"。

**没有引用的部分**：本文对"为什么这样改"的判断全部是产品判断，不是文献结论。文献层另见 `docs/参考资料/索引.md`。

## 8. 顺序与验收

```text
S6-0 修回四条红 ──► S6-1 令牌收口 ──► S6-2 过程账本 ──► S6-3 周回合/结算 ──► S6-4 单条裁决 ──► S6-5 版本链回看
                                          └──────────────── S6-6 表情可归因（与 S6-2 同批）────────────────┘
```

- S6-1 的验收是"契约扫到了 186 个色"，不是"看着像换了皮"。
- S6-2 + S6-6 一起做：账本要有数字，表情要由数字驱动，两者同一批数据。
- S6-4 / S6-5 可以推迟到试点之后——它们提升的是"互动感"，而 P4 观察的流失点大概率在 S6-2/S6-3 之前那一步（用户看不懂自己在干嘛）。
- **任何一片都不许在 `scripts\verify.ps1` 之外用截图代替判据**，除非是"逐字竖排"那类只有眼睛能发现的缺陷（沿用 §51/§52 的分工）。
