# 岗位卡片与成长档案规划

日期：2026-10-24  
状态：待实施；本轮仅核对现状并制定产品、交互和接入方案，没有改动生产功能。

## 1. 产品主线

**穗奈通过对话帮助用户认识自己；岗位卡片提供可以操作的现实参照；成长档案记录用户确认的经历、方向和实践积累。**

主线为：聊真实经历 → 检索岗位样本 → 对照要求 → 保留候选与探索方向 → 完成一个小行动 → 用结果更新档案 → 按需形成简历。

不另建一套填表主流程，也不让工作台默认占据主屏。聊天是行动入口，工作台是按需打开的记录窗口。

必须分开以下概念：

| 对象 | 表达的含义 | 不能自动推导成 |
| --- | --- | --- |
| 职业方向 | 后端、前端、AI 应用等参考方向 | 某公司正在招人的岗位 |
| 岗位样本 | 库内或用户提供的一份具体 JD | 当前仍在招、用户满足全部门槛 |
| 收藏 | 我想保留这份资料 | 我决定从事这个方向 |
| 探索方向 | 我想进一步了解或验证 | 唯一、永久的职业定位 |
| 已确认技能 | 用户确认、带依据的技能记录 | 企业认证、客观能力排名 |
| 学习目标 | 我准备学习的内容 | 我已经会的技能 |

## 3. 推荐链路：库内候选 + 可解释对照

### 3.1 工作流程

1. 读取用户主动提供的背景、已确认档案和明确约束；缺少关键信息时只追问一个最有影响的问题。
2. 复用岗位检索工具筛选候选；不擅自放宽城市、求职阶段等明确条件。
3. 读取候选完整 JD，核对学历、专业、经验、工作内容与技能要求。只出现关键词不足以证明满足条件。
4. 对照用户证据，逐项标记“有依据 / 部分有依据 / 待了解 / 存在冲突”。缺材料不等于不会。
5. 首次通常展示 2—3 张卡片。这是展示密度选择，不是算法保证；符合条件的只有一条就展示一条，没有就明确说明库的覆盖不足。
6. 用户可以收藏、查看详情、发起对照或确认探索方向，再决定是否进入学习、练习或简历步骤。

推荐理由必须区分：

- **岗位事实**：来自该 JD，可打开原文。
- **个人事实**：来自用户确认或明确提供的经历，可回看来源。
- **穗奈推断**：说明推断依据与待验证之处，不能伪装成确定事实。

不展示未经校准的匹配百分比、录用概率、竞争力排名。资料中的采集日期不等于今天仍在招聘。

### 3.2 结构化显示，而不是从文本猜卡片

新增一个受校验的展示工具，暂定名 `present_job_recommendations`。输入只包含库内 ID、理由、引文引用与需要进一步了解的内容；公司、标题、城市、薪资、日期等事实由服务端根据 ID 补全。

要求：

- 只能引用本轮已成功读取的岗位；验证 ID、内容指纹和引用，不接受模型自行创造的岗位。
- 推荐理由与具体个人证据关联；合理推断单独标识，不能把模型生成的引用当证据。
- 岗位卡片作为消息的结构化区块保存，不能依靠 Markdown 正则或最近若干条事件重新猜测。
- 流式文字与卡片独立渲染：合法工具结果返回后可以先显示卡片；还在生成的 JSON 不进入界面。
- 重试、页面刷新、会话切换与编辑重发均使用同一持久数据；失败续接不重复插入卡片。
- 旧分支按已有 `superseded_by` 规则退出当前消息流；用户此前明确收藏或确认的个人资料不静默回滚。

## 4. 页面布局

```text
┌────────────┬─────────────────────────────┬───────────────────┐
│ 职业工作台 │ 当前对话                    │ 穗奈小窗          │
│ 新建对话   │ 穗奈的简短说明              │                   │
│ 历史对话   │                             │ 成长档案摘要      │
│            │ 岗位卡片                    │ · 探索方向        │
│            │ 岗位卡片                    │ · 技能条目        │
│            │                             │                   │
│            │ 当前任务入口 + 输入框       │                   │
└────────────┴─────────────────────────────┴───────────────────┘
```

- 岗位卡片在对话中出现，不再增加常驻“推荐大屏”。
- 点卡片时，右侧已有预览区域切换为岗位详情；关闭后恢复穗奈小窗与档案摘要。详情不自动抢占用户正在编辑的窗口。
- 档案摘要替换/整合现在的“聊到了这里”区域，不额外堆一个同义面板；会话小结仍是会话小结，不能冒充全局已确认档案。
- 点档案摘要后打开现有工作台窗口中的档案页。工作台入口和窗口形式保持。
- 小屏详情使用可返回的全屏层；不挤成三栏。4K 使用有阅读宽度约束的内容区，不能把卡片拉成横跨整屏的长条。
- 继续使用现有像素字体、图标素材、主题令牌与后端素材入口；这一轮不要求重新生成角色或整套背景图。

## 5. 岗位卡片

### 5.1 收起态

示意内容不是库内实际岗位，也不是对当前用户的能力判断：

```text
后端开发工程师                              ☆
示例公司 · 示例城市 · 校招
Java / Spring Boot / SQL

可以继续了解：与你提到的服务端项目有交集。
需要核对：是否满足该岗位的毕业时间要求。

岗位参考 · 发布日期未知              和我对照 →
```

- 标题、公司、地点与招聘类型优先。薪资只在原文明确时展示，不推算缺失区间。
- 关键技能最多几项；有引用的原文提炼可以展示，无法确认时不强行补齐。
- 只保留一条最有用的理由和一条关键待核对项；不是每张都强制添加两行空话。
- 收藏为统一位置的星标图标；提供悬浮提示、无障碍名称和已收藏状态。
- 卡片主体打开详情，按钮有独立事件和键盘焦点，避免点击收藏却展开详情。
- “历史样本”“已截止”“状态待核实”等必要信息不能为精简样式而隐藏。

### 5.2 详情

默认先看岗位本身，“与我对照”按需展开：

1. **做什么**：职责与主要产出。
2. **需要什么**：学历、专业、经验、技术要求；分清必须与优先。原文未写的明确为未提及。
3. **JD 原文**：完整保留，提炼不能取代原文。
4. **来源与时间**：来源平台、原始链接、发布时间、采集时间和当前状态的核实边界。
5. **与我对照**：岗位要求与个人材料并排，指出已有关联、待补充证据与明确门槛冲突。

若公司、城市或学历等字段与原文冲突，保留原文和冲突提示，不让模型静默选择一个版本。

## 6. 操作语义

| 操作 | 实际效果 | 确认与边界 |
| --- | --- | --- |
| 查看详情 | 读取库内岗位、来源和已保存对照 | 不调用模型，不更新画像 |
| 收藏/取消收藏 | 保存/移除个人岗位引用 | 用户点击即可执行，幂等；取消可撤销，不删除公共岗位 |
| 和我对照 | 在当前对话用已有经历对照该 JD | 不新建会话；运行中显示进度，避免重复提交 |
| 加入下一步 | 选择一件具体任务，如核对门槛或补充项目证据 | 先看见任务内容再确认，一次只添加选中的行动 |
| 考虑这个方向 | 加入探索方向 | 先展示具体方向，不写成唯一目标 |
| 设为主要目标 | 调整当前主要探索/求职方向 | 显示新旧差异后确认；保留可比较的其他方向 |
| 请穗奈整理进档案 | 生成范围明确的档案变更建议 | 用户确认前只存建议；不把 JD 的技能写成用户已有技能 |
| 不感兴趣 | 降低这份候选再次出现的机会 | 默认仅针对该岗位；不能自动推断用户讨厌整个行业 |

“加入下一步”不是“收藏”的别名。例如收藏后端岗位后，下一步可以是“补一段接口压测与排错的项目说明”，而不是自动建立五个学习任务。

**收藏 ≠ 对照材料 ≠ 投递台账。** 收藏使用轻量引用，可分页；旧工作台 8 份对照材料的上限继续单独处理，达到上限时明确让用户管理，不删收藏、不无声覆盖。

用户从卡片发起的任务仍进入当前对话，不增加“简历工坊”等平行主入口。

## 7. 成长档案

暂定对外名称：**我的成长档案**。内容分为：

- **穗奈眼中的你**：短摘要，明确哪些是已确认内容、哪些仍待确认；可以修正。
- **正在探索**：主要方向、比较中的备选方向，以及用户选择的理由。
- **技能图鉴**：技能名称、记录阶段、证据入口和下一步实践。
- **做过的事**：项目、比赛、工作和行动结果，按实际贡献描述。

首版右侧摘要只显示几条最重要的内容，不把完整信息面板常驻展开。

### 7.1 两种记录状态

1. **穗奈整理的草稿**：可以从已发送的聊天中持续提取，注明来源并等待用户确认；不从输入框未发送的草稿推断。
2. **本人确认的档案**：用于后续岗位对照和简历事实引用，保留确认时间、来源与修订版本。

聊天小结更新不等于已确认档案更新。用户纠正时，新的确认替代旧内容，相关对照应提示需要重新评估，而不是无声改变结论。

### 7.2 技能等级：游戏式外观，实践记录语义

首版采用下列产品内阶段；它们不是职业资格、考试成绩或客观能力认证：

| 显示 | 记录条件示意 |
| --- | --- |
| 待了解 | 材料不足；不能写成 Lv.0、不会或能力低 |
| Lv.1 · 开始接触 | 用户明确提到学习或完成过基础练习 |
| Lv.2 · 项目实践 | 能关联具体项目与本人使用这项技能的内容 |
| Lv.3 · 独立完成 | 对一个明确任务有独立贡献、结果与排错/取舍的具体描述 |

阶段定义是待实现的产品规则，不是对现有用户的评级。先做到这三个可解释阶段，不急于增加“精通/大师”等权威感过强的等级。

证据来源另有一条独立维度：本人描述、已提供的项目/文档、行动产出。**本人点击确认不等于独立验证**；有材料不等于代码或效果已经被审查。

每项技能点开可以看到：

- 记录了什么，来自哪条消息、哪份材料或哪个行动。
- 阶段为什么这样显示，是否存在未确认的推断。
- 用户是否认可；可以纠正名称或阶段。
- 下一项与目标岗位有关的实践建议。

技能阶段变更必须由可解释规则提出并经用户确认，不能按聊天次数、在线时间、收藏数或穗奈好感度升级。

已会技能与学习清单分开：计划学习 React 不产生 React 等级；用户说“只是跟教程做过”不能自动升级成独立交付。

像素技能条可以显示几个阶段节点；不显示没有量表依据的“Java 87/100”。动画用于确认新记录或完成行动，不用于制造能力增长的假象。

## 8. 画像更新的确认方式

穗奈在当前对话内给出小范围变更预览：

```text
准备更新你的档案
+ 正在探索：后端开发
+ 选择原因：希望继续了解服务端业务与工程实践

[确认更新]  [改一下]
```

这只是示意；真实内容必须来自用户的选择与表述。

- 用户点“确认更新”就是该次明确的确认，不再套多层弹窗。
- 收藏等低风险、确定性操作不强制模型介入。
- 模型推断不能替用户点击确认；缺少关键事实时先问。
- 复用现有 `revision`、`context_version` 与 proposal 机制，旧版本建议不能覆盖新事实。
- 方向更新只改方向，技能更新只改相关技能，不让一次确认连带重写整份画像。

## 9. 数据与接入原则

**只维护当前 SQLite 主库，不引入第二个资料库或靠浏览器 localStorage 存正式收藏。**

### 推荐区块

扩展消息持久化数据，例如 `ui_blocks: [{type: 'job_recommendations', ...}]`，保存推荐 ID、岗位 ID/内容指纹、个人档案版本、理由与引用。

事件用于实时更新，消息快照用于刷新恢复。不能只依赖 `recentEvents`，因为现有最近事件接口有数量限制。

### 收藏

在主库增加个人收藏关系，建议独立轻量表 `career_saved_jobs`：用户、库内岗位 ID、收藏时间、备注/意向状态。用户与岗位 ID 唯一，所有读写校验账号归属。

收藏保留引用，不重复维护岗位正文。需要用于历史对照的固定证据快照，继续沿用现有岗位材料快照与内容指纹机制。

### 档案与技能

扩展同一个 `CareerState` 的结构化方向、技能和来源字段，沿用现有版本与确认机制。原有技能长文本先保留为历史资料，不直接拆成确定等级。

结构化技能成为后续技能视图的依据；旧文本只能作为可追溯来源或兼容投影，不能要求两份“技能真相”长期手工同步。

### 行动

复用现有成长行动的 todo / doing / done 与完成材料字段，不另建一套任务引擎。记录完成结果后穗奈可以提出档案变更，但完成任务本身不自动证明技能升级。

### 删除、更新与隐私

- 公共岗位更新或下架时，收藏显示变化，不能继续当作当前在招；已确认的历史对照保留原引用版本。
- 删除或编辑作为依据的对话时，关联事实需重新检查；已明确独立保存的档案仍可保留，但要说明来源已删除并允许一并移除，不能留下失效的“已验证”标记。
- 取消收藏不删除已确认画像或行动；删除个人行动不影响公共岗位库。
- 不把私有简历和聊天自动合并进公共岗位库。

## 10. 实施顺序

### 第一批：岗位真的可点、可留

1. 结构化推荐区块与消息持久化。
2. 对话岗位卡片与复用侧栏的 JD 详情。
3. 收藏/取消收藏；工作台里的个人候选列表。
4. 原有职业方向工具与具体岗位卡片的显示区分。

交付判断：用户在一段对话里看到真实库内岗位，能看原文、收藏，刷新或重进会话后仍在。

### 第二批：候选能变成决策与行动

1. 对照本人经历与 JD，显示引用和待核对项。
2. 卡片操作转为一个明确的成长行动。
3. 探索方向/主要目标的局部确认与更新。
4. 确认预览放在对话中，不要求先打开工作台填表。

交付判断：用户能解释为什么考虑这个方向，以及下一步准备验证什么。

### 第三批：档案成为可感知的成长记录

1. 右侧档案摘要与完整档案视图。
2. 技能结构化、三个实践阶段与证据详情。
3. 行动结果触发有依据的更新建议。
4. 学习与简历复用确认后的资料，不重复询问已有事实。

交付判断：用户能看懂“穗奈记录了什么、依据是什么、我下一步可以做什么”，而不只是看到等级装饰。

不在本轮做：实时岗位抓取、自动投递、社交排行、好感度/压力数值、无来源的能力评分、完整课程和题库平台。

## 11. 定向验收，不跑无关大验收

- 推荐区块只引用可读取的真实岗位；详情数据来自服务端。
- 未知、历史和截止状态正确显示；没有结果不编造公司或自动放宽条件。
- 收藏可恢复、去重、账号隔离，不受 8 份对照材料上限误伤。
- 刷新、切换会话、编辑重发与失败续接不产生幽灵卡片或重复待办。
- 收藏不改画像；方向确认不把 JD 要求写成用户技能。
- 档案变更先预览，版本冲突不覆盖；技能待了解不被显示为能力差。
- 点击岗位、收藏、对照和下一步各有独立且可键盘使用的入口。
- 大屏与小屏都保持聊天为主、详情按需打开；关闭详情恢复原布局。

## 12. 本轮结论

先实现“岗位卡片 → 详情 → 收藏”的最短闭环，再接方向确认、成长行动与技能档案。不是先堆更多功能，而是让每次对话都留下用户看得懂、能操作、能回看的具体结果。
