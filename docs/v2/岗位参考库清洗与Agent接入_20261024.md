# 岗位参考库清洗与当前 Agent 接入（2026-10-24）

## 产品边界

这不是实时招聘平台，而是供穗奈在对话中检索、解释和对照的历史岗位参考库。首版先复用已有数据；先跑通闭环，不把有限样本包装成全面市场推荐。

- 25 个方向保留介绍、典型工作、技能、成长路径、常见误区；它们是待审核的整理内容，不是市场事实。
- 旧库 808 行中，8 条演示数据不进入检索，177 条历史岗位因清洗后正文不足 80 字暂不进入检索，另隔离 4 条保留集合中的完全重复记录。
- 默认检索包保留 619 条历史岗位。长度阈值只是本版质量规则，不证明真实性；未删除、修改原 MySQL 数据。
- 清洗包括 HTML 标签与脚本去除、实体解码、空白整理、明确的城市尾部 None 占位清理；保留原始正文和来源 ID、链接、内容哈希。
- 不把 source.status=active 当成“2026 年仍在招”，不填造学历、年限或采集时间，不复用 1022 条 pending 方向关联。

## 现有覆盖是否足够

足够用作初版流程样本，但不足以支撑覆盖多专业、多城市、多求职阶段的普遍岗位建议。

清洗后按标题规则检索：前端 12 条、后端 35 条、测试/质量 60 条、产品经理 5 条。它们是**规则命中数量**，不是已审核分类、市场规模，也不能简单相加（规则可能重叠）。多个方向在当前标题规则下没有结果，需要补充数据并核查分类漏检。

619 条中，正文或标题出现“实习”的有 44 条，出现应届/校招等字样的有 77 条；这些仅是关键词线索，可能包含否定、无关描述，不能称为已确认的实习/校招岗位数量。

后续应先明确首批用户和主打方向，优先补齐对应方向的近期实习/校招样本，而不是平均给所有方向堆数量。可将每个主打方向 20–30 条经过核查的 JD 作为第一轮收集目标，**这只是启动目标，不是统计代表性保证**。方向、城市、阶段、日期、来源应分别检查覆盖；库里没有不等于市场上没有。

## 当前实现

运行时从唯一 SQLite 主库读取岗位、方向和原始交付，不要求运行旧 Python 服务或 MySQL；`agent/data` 下的 JSON 副本不属于当前运行链路。

Agent 新增只读工具：

1. `list_career_directions`：检索方向资料及标题规则样本数量。
2. `search_job_samples`：按关键词、城市、方向标题规则和阶段字样检索；上限 5 条，不显示适合度百分比，不自动放宽用户条件。
3. `read_job_sample`：读取完整清洗后的 JD、来源和时效限制。

保存沿用 `propose_career_update`，新增 `data.kind=catalogue_job` 和 `catalogue_id`。模型只提交 ID；服务端固定原文与出处快照，用户在原有工作台确认后才加入个人岗位材料。随后沿用现有职业对照和成长行动工具。保留当前工作台最多 8 份个人岗位材料的限制；这不是公共库只能存 8 条。

确认前可看原文与原始链接，确认后始终标记“历史样本、采集时间未知”。个人导入的 JD 仍属于个人工作台，不会被自动汇入公共库。

这次没有自动将岗位写进简历事实库，没有新增招聘抓取器、投递功能、完整课程/题库，也没有承诺任意第三方模型都能稳定选对工具。

## 接口

均要求登录：

- `GET /api/v1/agent/career/catalogue/directions?query=...&limit=8`
- `GET /api/v1/agent/career/catalogue/jobs?query=...&city=...&direction_code=...&audience=any&limit=3`
- `GET /api/v1/agent/career/catalogue/jobs/:id`

`audience` 可用 `any`、`internship_mentioned`、`graduate_mentioned`，仅表示原文线索，不是经审核岗位类型。

## 更新数据

在项目根目录执行：

```powershell
python scripts/export-job-catalogue.py
```

脚本只读现有配置中的数据库连接，输出默认静态包及 `logs/job-catalogue-integration-20261024/cleaning-report.json`，不输出密码或 API Key。数据更新后需重启 Agent 以装载新快照；导出时间不是招聘采集时间。后续新鲜数据接入需扩展来源与时效元数据，不能把旧数据统一打成当天采集。
