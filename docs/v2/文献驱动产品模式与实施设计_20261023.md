- 阅读声明：资料目录有 44 份 PDF，已有提取索引；**提取不是通读**。本文件只采纳下文列出的相关章节，不把整个参考库当成已核实证据。

## 1. 先给结论：方向值得做，但不能“读到一个模式就认为产品成立”

**推荐定位：穗奈是一个基于用户真实材料和岗位证据、能持续推进求职与成长任务的职业行动助手。**

它不是替用户判定“天生适合哪种职业”的测评器，也不应退化为一个会聊天的简历排版器。需要打通的是：

> 整理经历与约束 → 确认可修改的职业档案 → 提出/比较候选方向 → 对照真实岗位材料 → 明确缺口与未知 → 学习和实践 → 收回新材料 → 更新判断。

简历、学习清单、练习题、面试准备和发展路线，是这个过程的不同交付物。

**这一定位主要来自用户明确提出的需求和项目原有目标，不是三篇技术论文直接证明的“最佳产品模式”。**技术原文帮助我们规定“怎么避免假完成、伪引用和无依据结论”，不能证明使用本产品会提升录用率。

对此前建议的修正：“先做简历工作室”可以是入口和演示切片，但不应在缺乏依据时取代整个职业规划主线。

## 2. 需要区分的四种依据

| 类别 | 在本项目中的作用 | 不能偷换成什么 |
| --- | --- | --- |
| 用户原始需求 | 决定要解决哪些任务 | 不能等同于所有用户都有同样需求 |
| 论文原文 | 支撑特定技术机制或评测口径 | 不能等同于本产品已经有效 |
| 产品与工程判断 | 在时间、成本和现有代码下选择实现方式 | 不能包装成论文结论 |
| 项目实测 | 证明指定版本、配置和案例下的表现 | 不能推广成普遍就业效果 |

文献数量、页面复杂度、角色动画数量，都不直接等于产品说服力。

### 3.1 原文与其他 Agent 笔记的差异

1. **ALCE 的分母不能漏掉未引用的陈述。**现有笔记前面的原文摘要基本写对，但“建议改门禁”部分把分母写成“带至少一条引文的陈述数”。这会隐藏缺引用的问题。若项目只评估需要依据的事实断言，应先定义并固定断言集合，再统计其中获得充分引文支持的比例；漏引的断言不能从分母消失。该项目口径应另命名，不能声称完整复刻 ALCE。
2. **AbstentionBench 的 precision 摘要写反。**笔记第 [09] 节写作“弃答中不该弃答的比例”；以正确弃答为正类时，精确率是“实际弃答中确实应当弃答的比例”。笔记后面的详细公式又写对了，属于内部不一致，不能整份直接照抄。
3. **文本弃答、临时建议、写入审批是三件事。**允许给暂定建议不等于允许保存为已确认事实；用户同意写入也不等于外部事实已经验证。
4. **旧版测试数字不能作为新版结果。**参考笔记中的旧门禁、38 条案例和业务对象，需对照当前 TypeScript 代码重新建立映射，不能直接继承其通过结论。

原始笔记保留不改；逐项核对记录见本文件末尾的日志链接。

## 4. 四种产品路线的取舍

以下为产品判断，不是论文排名。

| 路线 | 能解决什么 | 当前代价或缺口 | 建议 |
| --- | --- | --- | --- |
| 通用 Agent + 穗奈与像素界面 | 对话、调用工具、生成文件 | 没有稳定的职业领域状态，很容易与通用产品同质化 | 保留为底座，不作为最终差异点 |
| 简历工作室为主 | 输出具体，便于展示上传、优化与导出 | 覆盖不了“不知道选什么方向”“该学什么”“如何持续成长” | 保留为明确入口与成果 |
| 固定问卷 + 适配度分数 | 流程容易搭建、表面直观 | 本轮没有核实能支持其推荐效度的依据；容易把模型主观判断伪装成精确分数 | 不作为主线；不自行拼量表并宣称有效 |
| **有档案、有来源、有行动回收的职业助手** | 能把用户提出的核心任务串成可迭代过程 | 需要领域数据、确认机制和真实任务验收，不能只加提示词 | **作为当前优先设计假设** |

不建议再重写一遍通用 Agent，也不建议先堆多 Agent、向量库或复杂编排框架。先用现有单 Agent、少量领域工具、确定性校验和持久化状态跑通一条主线；这是对范围与成本的选择，并非论文证明“单 Agent 永远最优”。

## 5. 产品体验：同一份档案，三个入口，不强迫走长流程

### A. 我还不知道找什么工作

穗奈先问缺失的关键问题，整理用户主动提供的经历、技能、意愿和现实约束。用户确认之后，才形成长期档案。接着提出少量候选方向，并说明每个方向的依据、反向证据、尚缺的资料和下一步行动。

画像在这里是**可编辑的材料摘要**，不是人格诊断，也不是给用户贴一辈子的标签。

### B. 我有目标岗位，想知道差多少

用户提供目标岗位的招聘描述（JD）。穗奈提取要求，并逐项对照用户已确认的经历：

| 岗位要求 | 档案/作品中的依据 | 当前状态 | 下一步 |
| --- | --- | --- | --- |
| 某项技能 | 指向具体项目或用户陈述 | 已有材料 / 材料不足 / 有冲突 | 补充说明、练习或作品 |

“简历中没写”只能说明缺材料，不能直接断言用户不会。单条 JD 只是样本，不能推断整个行业、薪酬水平或录用概率。

### C. 我已有简历，想优化或从模板写一份

允许直接上传或粘贴简历，不强制先填完全部画像。先核对提取结果与事实，再结合目标岗位修改表达。每条经历、技能和数字应有原始依据；没有依据就追问，不编造。模板决定排版，不决定事实。

最终提供真实的可预览文件和下载/本地打开能力；云端文件下载需要鉴权，不能把服务器路径当成用户能打开的位置。

### 用户最初提出的功能如何接到主线

| 需求 | 领域机制 | 最小可见结果 |
| --- | --- | --- |
| 构建画像 | 材料提取 + 用户确认 + 可修改版本 | 一份可编辑档案，区分自述、材料和推断 |
| 推荐岗位 | 候选方向 + 实际 JD + 对照理由 | 候选清单，而非“命定职业” |
| 学什么 | 要求与现有证据的差距 | 对应到岗位要求的学习与实践清单 |
| 题库 | 练习目标与岗位要求对应，答案/评价规则可核对 | 小规模能力练习集，不冒充企业真实题库 |
| 发展路线 | 目标、阶段性行动、材料与复盘 | 可调整的近期行动与阶段路线，不保证固定晋升 |
| 制作/优化简历 | 已确认经历 + 岗位材料 + 模板渲染 | 有依据的简历版本、差异和真实文件 |

穗奈的形象与动画用于反馈“正在提取、等待确认、已生成、遇到问题”，不替代这些业务状态。

## 6. 当前代码真正缺的是什么

核对的是 2026-10-23 工作区静态代码；本轮没有重新运行全量应用验收。

| 已核对位置 | 可确认的现状 | 对实施的含义 |
| --- | --- | --- |
| 根 package.json | 默认开发/构建指向 agent/ 与 web/；旧 Python 需显式 legacy 入口 | 以 TypeScript 主线设计，不照搬历史架构 |
| agent/src/tools.ts | 工具以文件、计划、追问、导出和命令执行为主 | 不等于已具有职业档案、岗位证据或路线更新机制 |
| agent/src/runtime.ts | 系统说明定位为通用可靠任务助手，并有权限/原件约束 | 加职业称呼还不够，需要真实领域数据和工具 |
| agent/src/profiles.ts、store.ts | profiles 存的是模型连接配置 | 不能误称已经有用户职业画像库 |
| agent/src/files.ts | 当前导入白名单为 UTF-8 文本类，明确要求 PDF、Word 先转文本 | 正式的简历上传体验仍需解析、质量提示和原件保留 |
| docs/v2/PROJECT_GOAL.md | 原本已有“决策—行动—复盘”目标，但实现描述属于旧阶段 | 可以沿用目标，不沿用“已完成”状态和旧测试数字 |

当前问题不是“没有一个通用 Agent”，而是**职业领域闭环还没有完整接回当前底座**。

## 7. 最小领域层：少建概念，但把事实分清

### 7.1 只新增必要的业务对象（提案，尚未实现）

- **CareerCase**：用户的一项职业/求职目标，关联档案、岗位样本、行动和成果，归属到用户；不同对话可在明确授权范围内引用。
- **ProfileFact**：一条经历、技能自述、偏好或约束。保存来源、用户确认状态与版本；确认只表示用户认可，不等于第三方核实。
- **Source**：简历原件、JD、作品或用户材料；保存文件/URL、摘要位置、获取时间、适用范围与内容版本。
- **Claim / Comparison**：一条结论及其支持/冲突材料、缺口、推断标识；引用具体档案与来源版本，不让模型口头虚构来源 ID。
- **Action**：要做什么、为什么做、完成材料是什么、当前进度、用户反馈；不只是生成一个待办文本。
- **Artifact**：复用现有文件成果机制，扩展职业上下文与引用快照，不另造第二套下载系统。

不把“确定性百分比”作为必填字段。没有经过校准的模型数字，不应叫“适合度”或“录用概率”。

### 7.2 工具与代码责任

建议只暴露少量领域入口：读取职业上下文、提出档案变更、导入/提取岗位材料、生成带证据的比较或计划、记录用户提交的行动材料。简历排版与文件校验由后端服务完成，复用既有成果发布入口。

- LLM 负责理解意图、追问、选择下一步和起草内容。
- 代码负责用户归属、来源 ID 是否存在、输入是否有效、审批、版本、工具权限和真实文件状态。
- “应用已批准变更”由服务端验证批准记录后执行，不能让模型传一个 approved=true 就绕过。
- 用户修正一条经历后，依赖旧版本的比较与简历标为待更新；不悄悄重写历史版本。
- 外部资料中的提示词按数据处理，不得改变权限或触发任意命令。

### 7.3 第一条可运行闭环

先用现有可处理的文本材料降低解析阻塞：

> 用户粘贴经历/简历与两份岗位材料 → 穗奈提出档案草稿 → 用户确认/修正 → 输出逐项证据对照 → 用户选择下一项学习/实践行动 → 提交一份新材料 → 系统更新相应判断并保留旧版。

“两份”和“一项”只是本轮收窄开发范围的工程选择，不是论文给出的最优数量。允许用户已有目标时只处理一个岗位；没有 JD 时可以先生成待验证方向，但不伪造招聘证据。

这条闭环跑通后，再接正式 PDF/DOCX 导入、模板简历与导出；练习题和长路线依赖同一份要求—证据映射，不另开互相割裂的产品。

## 8. 先验收什么，才能有说服力

### 8.1 工程正确性：看真实状态，不看模型的完成宣言

使用明确的测试材料和隔离账号/临时目录，逐项断言：

1. 未批准的档案建议没有变成已确认事实；跨用户访问被拒绝。
2. 每个来源 ID 与原始摘录确实存在，无法解析的文件不伪装成功。
3. 导出文件存在、可打开、版本与用户确认内容一致，原始简历未被覆盖。
4. 停止、重试和恢复不会重复写入或重复批准。
5. 外部内容不能通过提示词改变权限或泄露密钥；日志不保存完整简历、密钥等不必要敏感内容。
6. 云端成果链接经用户身份校验，不能猜 ID 获取他人文件。

以上属于必须满足的项目规则，不是论文报告的结果。

### 8.2 内容依据：不能用“有链接”代替“有支持”

对岗位要求、技能断言等需要依据的事实单元，区分：来源存在、摘录真实、摘录是否充分支持断言、材料范围是否足以支持所作推广。建议与事实分开标识。

项目指标建议命名为“需依据事实断言的支持覆盖率”：

> 获得充分支持的需依据事实断言数 / 全部需依据事实断言数。

未引用、引用不存在、仅支持一半的断言不能算充分支持；不应因没有引用就把它剔出分母。无可评估断言时记为不适用，不记为 100%。自动模型判分只作辅助，必须保留可逐项核对的标注与失败案例。

### 8.3 缺信息与权限：分开验收

- 材料不够：应指出缺什么、询问或给带边界的暂定建议。
- 已有足够材料：不应无意义地反复追问。
- 无写入授权：即使结论有充分依据，也不能越权写入。
- 已获写入授权：也不能把未知事实当成已验证事实。

不把 write_withheld、is_provisional 或“语气谨慎”单独当成可靠性的证明。

### 8.4 与通用 Agent 的区别：用同一套软件案例比较

固定相同的模型、配置、材料和任务，比较“现有通用模式”与“新增领域层”：

- 能否跨对话取回经授权的档案，而不是重新猜测；
- 档案修正后，是否正确找到并更新受影响的结论；
- 推荐、学习项、练习和简历是否引用同一套要求与事实；
- 文件与授权规则是否满足；
- 耗时、工具次数和费用增加是否可接受。

重复运行案例以观察一致性，借鉴 R2 的 pass^k 思路，不把“多试几次总有一次成功”误当稳定。这里不设“应该推荐哪个唯一职业”的金标。

这些实测最多支持“在这些任务中更完整、可追溯或稳定”，不能写成“已证明提高求职成功率”。

## 9. 接下来按什么顺序做

### 第一阶段：先定数据与样例，不继续换皮

- 把本提案转为少量具体输入/预期输出样例，覆盖“方向不明、有目标、有简历”三个入口。
- 定义档案事实、来源、结论与行动的最小字段和确认规则。
- 对照真实赛题逐条建立“要求—能力—证据”矩阵；**该赛题正文尚未在本轮完成核验，暂不声称合规。**

### 第二阶段：接通最小领域闭环

在现有 TypeScript Agent 上增加领域持久化和少量工具，优先做确认档案、证据对照、行动回收。沿用现有对话、文件预览和权限 UI，只有状态表达不够时才改页面。

### 第三阶段：把用户能拿走的成果做好

接 PDF/DOCX 导入与提取校对、真实模板简历、导出验证；再把学习资源、练习和路线接到同一领域数据上。扫描件/OCR、复杂表格和外部资源的授权与准确性单独处理。

若仍按一周打磨，优先完成一条可演示、可复现的闭环；不能同时承诺通用 Agent、完整题库、全网岗位库和成熟简历编辑器。该时间顺序是范围建议，不是完成日期保证。

## 10. 需要主动防止的成本和偏差

- **来源成本**：一个 JD 不代表市场；岗位会过期，转载会重复。保存时间与范围，别把样本包装成市场统计。
- **隐私成本**：本地 WebUI 不代表简历留在本地；使用云端模型/第三方网关前明确告知数据去向，支持最小化发送与删除。
- **操作成本**：有“沙箱”名称不等于隔离已被证明；按当前执行环境实际边界设置权限与测试。
- **评测成本**：不为每段聊天增加多个模型裁判；确定性规则先做，重点事实再核对，记录费用和失败。
- **维护成本**：别维护两套领域状态、两套下载和两套确认；旧版代码可作为设计参考，不默认双线继续开发。
- **论证偏差**：不能先决定功能再挑支持的论文；每个采用理由同时记录不适用边界和什么结果会让我们改方案。

可以说：

> 本产品依据用户的职业任务需求设计持续更新的档案、岗位证据对照和行动回收流程；引文质量、任务状态检查和缺信息处理参考相关 Agent 技术评测方法。系统通过指定案例验证文件、授权、来源与版本一致性。

## 13. 首版落地记录（2026-10-23）

用户选定“工作台带对话”：左侧是页面与对话导航，中间是职业材料工作台，右侧保留穗奈对话；窄屏将对话改为可展开窗口。像素字体、原穗奈动态形象、模型设置、权限、执行记录和文件预览沿用现有实现。

本轮已接通的领域能力：

- 职业档案由用户填写或由模型提出草稿，用户确认后保存；同一账号跨对话读取。
- 岗位以用户粘贴的招聘原文作为样本，模型分析要引用原要求和个人材料；缺材料标为未知。
- 成长行动记录原因、学习内容、预期材料和完成结果；新结果可用于下一次岗位对照。
- 模型通过 read_career_context 读取领域状态，通过 propose_career_update 提出草稿；模型不能直接确认或覆盖档案。
- 服务端检查资料版本与引文是否存在。接受的历史对照会保留；材料变化后标记旧判断待更新。引文存在仍不代表分析正确。
- 简历与文件页复用真实对话文件、预览与下载。文件目前仍按对话保存，PDF/DOCX 内容提取尚未接通。

验证范围：新增职业流程与既有运行核心共 19 项后端测试通过；相关前端 23 项测试通过，类型检查及生产构建通过。Chrome 实际检查了档案保存、岗位添加、行动完成、刷新持久化、固定测试草稿确认、文件预览和 1440/3840/430 像素宽度布局。运行核心里的模型是测试替身；浏览器中的固定分析明确标为测试草稿。本轮未调用真实第三方模型，不据此声称职业判断有效性或比赛合规。
